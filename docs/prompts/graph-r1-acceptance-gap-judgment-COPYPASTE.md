# PRODUCT LOCK（変更禁止の前提）

SUGUDASU Graph の一次価値:

> Excel をコピー → SUGUDASU に貼る → グラフができる → Slides/PPT に貼る  
> **編集しなくても、そのまま資料に使える**

成功条件:

> 描画できた ≠ 成功  
> **約3分で実務資料に貼れる = 成功**

**手戻りコスト（必須）:**

実務では次が起きうる。

```text
作る → Slides に貼る → 「思ったより読めない」 → SUGUDASU に戻る → やり直す → また貼る
```

これは「3分」を壊す。特に **Slides / PPT 2019 などへの SVG 貼付は貼付側で直せない**ので、**一発で使えるデフォルト**の価値がさらに上がる。

裁定での扱い:

| 事実 | 効き方 |
|------|--------|
| 貼ってから可読性不足に気づく | Gap A/C/B-fill の欠陥重要度↑（出荷前に潰せ） |
| 手戻りが「色をいじる編集UI」になる | **REJECT**（Editor 化。Pain の再実装） |
| 手戻りが必要なら | 許容は **データ修正 / Intent 再選択 / 配置スロット再選択 → 再出力** まで。図の中を直させない |
| 「一回貼ってダメなら直せばいい」 | HOLD / 延期の正当化に **使わない**（手戻り前提は失敗） |
| **JSON 一時保存で手戻りを救う** | **主解にしない**（下記「Continue Later / JSON」） |

### Continue Later / JSON（裁定で混ぜるな）

SUGUDASU 全体には「続きを開く」（Continue Later · 端末内 JSON / IndexedDB）がある。  
ただし Graph の一次フローは **数分で貼って終わる**。PDF記入のような「95%終わって印鑑待ち」とは性質が違う。

| ニーズ | R1 での扱い |
|--------|-------------|
| 貼付後の可読性不足の手戻り | **デフォルト品質で一発化**が本命。保存機能では解けない |
| タブを閉じた・ブラウザ落ち | Continue Later Level 1 は将来候補だが、**今の Gap A/B/C 裁定の主題ではない** |
| Graph Spec / Intent の JSON ダウンロード | 開発・再現・スロット再レンダ用には有用。**一般ユーザーの一次CTAではない** |
| 「下書きを保存して色を後で直す」 | Editor 化の入口 → **REJECT 寄り** |

裁定で「JSONを一時保存すればよい」を Gap A/B/C の解にしてはいけない。

固定判断（すでにシニア3役で確定）:

- R1 Renderer（Bar / Column / Line）= GO 継続
- R2（Waterfall / Scatter / Donut 等の種別拡大）= **HOLD**
- Graph Editor / 色・線幅・凡例・軸の編集UI / テーマエディタ = **禁止**
- Renderer は `matched_rule_id` / `intent` / `RLE-*` を見て分岐しない
- 「貼ったあとに直したくなる」は、まず **Renderer デフォルト不足** を疑う
- SVG を Illustrator 等で後加工できることは **二次価値**（一般ユーザー向け KPI にしない）

### 貼付先による重要度（必須加重）

| 貼付先 | 貼ったあと | デフォルト欠陥（文字切れ・余白・線・可読性）の重要度 |
|--------|------------|------------------------------------------------------|
| **Google Slides へ SVG** | **実質編集不可** | **最高** — 出力時点で完成必須 |
| **PowerPoint 2019 へ SVG** | **編集できない（観測）** | **最高** — Slides と同格。分解・文字直しを期待するな |
| PowerPoint 新しめ / 一部環境 | 図形に変換できる場合あり（不確実） | 高 — **環境依存の救済は一次解にしない** |
| PNG | 画素として固定。編集不可 | 高（同様に完成必須） |

観測ロック（2026-08-08）:

> **PPT 2019 では SVG が編集できないっぽい。**  
> 「PowerPoint なら貼ったあと直せる」は **一般解として使えない**（少なくとも 2019 世代では）。

### 理想と現実（貼付後微調整）— 混ぜるな

質問者の追加心情（正当）:

> 実際には、**PPT に貼り付けてから微調整できるのが一番**なのだろう。

これは否定しない。ただし次を分離せよ:

| 層 | 内容 | 扱い |
|----|------|------|
| **理想 UX** | 貼る → PPT/Keynote 上で位置・大きさ・文言を少し直す | 人間の自然な資料作り。**二次価値** |
| **一次解（SUGUDASU）** | 貼った瞬間に読める・意味が通じる | **必須**。3分・編集UI禁止と整合 |
| **環境依存の救済** | 新しい PPT で図形変換できる等 | **ボーナス**。Acceptance の合否条件にしない |
| **SUGUDASU 内 Graph Editor** | 色・字号・DnD をアプリ内でやる | **禁止**（Pain の再実装） |

裁定ルール:

1. 「PPTで微調整できるのが一番」を認めてもよい。**ただし Gap A/B/C の HOLD・REJECT 理由にしてはいけない**（Slides / PPT2019 では救済できない）
2. 一次解は引き続き **デフォルト品質 +（必要なら）配置スロットに合わせた canvas/字号**
3. 二次価値として「貼付先でいじりやすい出力」（レイヤー分離済み SVG、将来の EMF 等）を **ボーナス候補** として触れてよい。今の GO-NOW 必須にはしない
4. 「微調整したい」＝ SUGUDASU に字号スライダーを作れ、ではない
5. 理想（貼ってから直す）と現実（多くの経路で直せない）が衝突したら、**現実側（一発完成）を勝たせる**

したがって:

> **Slides / PPT2019 への SVG 貼付では、「あとで直せばいい」は REJECT 理由にも延期理由にも使えない。**  
> 文字切れ・ラベル欠けは、編集UI需要ではなく **出荷ブロッカー級のデフォルト品質欠陥** として扱う傾向を強めてよい。

### Slides 上の実サイズ（必須加重 · よくある運用）

Slides に貼る SVG は、**出力ピクセルのまま表示されるとは限らない**。

よくあること:

1. **スライド枠に合わせて比率固定で縮小**される（幅・高さともスケールダウン）
2. **左にグラフ・右にコメント**の半面配置で、グラフ占有幅がさらに半分近くになる
3. その結果、Renderer 上では読めていた **11px 文字・細い線・狭いラベル余白** が、実スライドでは読めなくなる

含意（裁定で使え）:

| 事実 | 裁定への効き方 |
|------|----------------|
| 縮小される | 「640×360 で読めた」だけでは合格にしない。**縮小後可読性**を疑う |
| 半面レイアウト | デフォルトは **フルブリード前提の細字**より、**半分幅でも読める字号・線幅・余白**側に寄せる判断を強めてよい |
| 編集不可 × 縮小 | 文字切れ・字が小さいは二重に致命。GO-NOW 寄りを正当化しやすい |
| **プレゼン作者の心情** | データ資料を作る人は Slides 上で **項目名や目盛をもっと大きくしたくなる**。これは編集欲ではなく **デフォルトが細すぎるサイン** |
| 意味表現（前年比等） | 縮小でさらに情報密度が苦しい。種別追加より **今ある単系列の可読デフォルト** を先に疑う材料にもなる |

**字号の解釈ロック:**

> 「Slides で文字を大きくしたくなる」＝ グラフエディタ需要、ではない。  
> ＝ **出力時点のカテゴリラベル・軸目盛・余白が、プレゼン距離・半面縮小に対して細い** というデフォルト品質ギャップ。

したがって Gap A / C の裁定では、単に「切れない」だけでなく、**プレゼンで「もう少し大きく」と思わせない字号・目盛**まで一次解に含めてよいかを述べよ（ユーザーに字号スライダーは渡さない）。

検証時の目安（厳密な px 契約ではない · ジャッジ用）:

- ワイドスライドでグラフが **おおよそ左半分**（コメント右側）に置かれたとき、カテゴリ名・軸目盛が読めるか
- 縮小後に線が消えず、棒の差が分かるか

### 出力キャンバスサイズ（Gap C の前提）

現行 R1 デフォルトは概ね **640×360**（汎用）。

質問者の仮説（固定したい方向性）:

> 基本的には **PowerPoint / Google Slides / OpenOffice·LibreOffice Impress / Keynote** など、  
> プレゼンテーションの **スライド寸法・配置スロットに合わせて、グラフサイズと文字サイズを調整したい**。

Slides 専用問題ではない。**デッキ系ツール共通**の出力前提である。

例（数値は仮 · 裁定で採用可否を決める）:

| スロット | 想定用途 | 方針の候補 |
|----------|----------|------------|
| `deck_half_left` | 左グラフ・右コメント（どのデッキでも頻出） | 半面幅前提の canvas で **字号・目盛・余白**まで決めて描く |
| `deck_full` | グラフが主視覚 | ワイド1枚ほぼ全面。字号も全面前提 |
| `generic` | 現行互換 | 640×360 等 |

別名として `slides_*` を使ってもよいが、意味は **デッキ共通**。

これは **グラフエディタではない**。  
「色をいじる」「自由な px 入力」ではなく、**貼る枠（スロット）を1つ選ぶ／デフォルトをデッキ寸法前提にする**程度の Presentation Setting 候補。

**セットで決めるもの（片方だけは不十分）:**

| 層 | 内容 |
|----|------|
| canvas | width × height（スロット） |
| type scale | カテゴリ名・軸目盛・（必要なら値ラベル）の字号 |
| stroke | 線幅（縮小後も残る太さ） |

裁定で切り分けよ:

1. **Aだけ直す**（固定 canvas のまま余白・字号を上げ、縮小耐性で殴る）
2. **Cを入れる**（デッキ寸法／スロット別 canvas + 連動する文字サイズ）
3. **A→様子見→C**（まずラベル切れを直し、半面貼付でまだ読めなければ C）

「自由な幅高さのカスタムUI」は Editor 寄りなので原則 REJECT。  
プリセット 2〜3 個までなら Presentation Settings 最小として許容しうるか、を述べよ。  
特定ツール（Slides だけ）に最適化し、PPT / Keynote / Impress を無視する案は弱い。

「Office で手作業ならグラフを作り直せる」は Pain の再実装であり、SUGUDASU の主解にしない。  
ただし **貼った表に存在しない意味を Renderer が発明してはいけない**。

# 判定対象ギャップ（Acceptance OA-05）

## Gap A — 長いカテゴリラベルが切れる

観測:

- OA-05（部門別売上・順位 · Bar）を **Google Slides に SVG 貼付**
- 「コーポレート」が左端で欠け、「-ポレート」のように見える
- Slides 上では SVG 内テキストを直して救済できない
- **追加リスク:** Slides が比率縮小する／左半分配置だと、切れ＋字が小さくなり可読性がさらに落ちる
- 原因仮説: Bar の左余白が固定（約 56px）。ラベルは text-anchor=end で軸左に置かれる

問い:

- 編集不可 × 縮小前提で、これは **GO-NOW（出荷ブロッカー）** か
- 「Acceptance 全部見てから」で遅らせてよいか（遅延コストを明示）
- 「ラベルをユーザーが短くする」「Slides で直せ」「フルサイズで読めればよい」は REJECT / HOLD 理由にしてよいか（原則 No）
- 余白修正だけでなく、**縮小耐性のある字号・線幅・目盛**まで同じ GO に含めるべきか（範囲を明示）
- 「項目名・目盛を大きくしたくなる」を、字号スライダーUIではなく **デッキ（PPT/Slides/Impress/Keynote）向けデフォルトの引き上げ** で解く案を評価せよ

## Gap B — 達成/乖離・前年比が「ひと目」で分からない（単色ベタ塗り含む）

観測:

- **IR だけではない。社内資料でも**「当初目標との乖離」「達成/未達」はとても大事な情報である
- 営業・事業部成績でも同様。順位棒だけでは仕事が終わらないことが多い
- 現行 R1 の単系列 Bar は **全カテゴリが同一色のベタ塗り** → スライド縮小後は特に、差が長さだけに依存し **視認性が悪い**
- PowerPoint / 汎用 Office でも Grouped Bar・目標線・達成色分けは **手作業なら** 作れる（それは Pain）

技術的事実（現行設計）:

| 欲しい意味 | 表に必要な列 | Decision 側 | R1 Renderer |
|------------|--------------|-------------|-------------|
| 順位・大小 | 部門 × 1指標 | Bar / Ranking | 描ける（現状は単色ベタ） |
| 前年比 | 今年＋前年など 2系列 | Grouped_Bar（例: RLE-013） | **R1外（HOLD）** |
| 達成/未達・乖離 | 実績＋目標 | TARGET_VS_ACTUAL → Bullet 等（確認あり） | **R1外** |

**絶対禁止:** OA-05 のような単系列で、目標列も前年列も無いのに「達成色」「前年比色」を発明すること。

裁定では Gap B を必要なら次に分けてよい（ただし主判定は1つ。サブは注記）:

| サブ | 内容 | 性質 |
|------|------|------|
| **B-data** | 目標/前年が表にあるときの描画（Grouped_Bar / target line / 達成色） | 意味は Spec。R1外の可能性大 → HOLD-R2 寄りか R1.x か |
| **B-fill** | 単系列でも「全部同じベタ塗り」が実務で弱いか | デフォルト品質。ただし **意味のない多色は禁止**（順位の長さを壊す装飾は Anti） |

問い:

- 社内＋IR の達成/乖離ニーズを踏まえ、Gap B の主判定は何か
- **B-fill**（単色ベタが弱い）を、目標データ無しの今、どう扱うか  
  - 例: 値ラベル必須 / ストライプなしで線・コントラストだけ上げる / 何もしない / HOLD  
  - 「カテゴリごとに別色」は意味が無いのに色を付ける行為になりうる — 許容条件を厳密に（原則は疑え）
- **B-data** はいつキューに入れるか（Acceptance 中 / HOLD-R2 / 目標列 fixture を先に取る）
- 「Office でできるから不要」は REJECT 理由になるか（通常はならない）
- 「ひと目」のために編集UI（色パレット）が必要、という結論は出してよいか（原則禁止）

最小実装を書く場合の制約:

- 目標がある → 達成/未達の色分けや目標線は **Spec の意味に従うデフォルト**（ユーザーが色を選ぶUIではない）
- 目標が無い → 嘘の達成色を出さない
- 単色ベタの改善は、意味を増やさず可読性だけ上げる手段に限る
## Gap C — 出力サイズ・字号をプレゼン寸法／配置スロットに合わせるか

観測 / 仮説:

- 汎用 640×360 で描き、デッキ側で比率縮小すると可読性が落ちる
- 対象は **PPT / Slides / Impress / Keynote**（Slides 専用問題ではない）
- 左グラフ・右コメントでは、最初から半面幅のキャンバスで描いた方が字号・余白の設計が素直
- API は既に `width` / `height` を受け取れるが、**プロダクトとしてのデフォルト／プリセット**は未固定
- 理想としては貼付後に PPT で微調整できるのが一番、だが **環境依存**（Slides・PPT2019 では不可）

問い:

- Gap C は **今 GO** か、**A の後**か、**HOLD** か
- 入れるなら最小は何か（例: デフォルトを `deck_half_left` 相当に変えるだけ / プリセット2つ / 自由サイズUIは禁止）
- C を入れても Decision/Spec 境界を壊さないか（Presentation Settings のみか）
- 「サイズを合わせる」と「縮小耐性のあるタイポ（項目名・目盛を大きく）」はどちらを一次解にするか（併記可だが主判定は1つ）
- スロット別 canvas にする場合、**半面スロットでは字号・目盛をさらに太く/大きくする**のがデフォルトか
- 「PPTで微調整できるのが一番」を理由に Gap C を **やらなくてよい** と結論してよいか（原則 No — 現実の非編集経路が残る）
- 逆に、貼付後微調整向けの **二次フォーマット**（図形化しやすさ等）を今の必須に含めるか（原則ボーナスのみ）

# 判定ルール

各 Gap に次のいずれか **1つ**:

| 判定 | 意味 |
|------|------|
| **GO-NOW** | 今すぐ実装してよい。Editor なし。境界を壊さない。R1 デフォルト品質の範囲 |
| **GO-AFTER-ACCEPTANCE** | Acceptance 15ケースの貼付結果を揃えてからまとめて直す |
| **HOLD-R1x** | R1 の「貼れる」検証が終わるまで触らない。終わったら別ジャッジ |
| **HOLD-R2** | グラフ種別・意味表現の拡張。現状の R2 HOLD に従う |
| **REJECT** | やらない / ユーザー責任 / 編集UI誘導 / データ発明 など憲法違反 |

追加で必ず答えること:

1. **一次価値への寄与**（3分・編集なし貼付に効くか）
2. **貼付後編集可能性**（特に Slides+SVG で救済できるか。できないなら欠陥重要度↑）
3. **縮小・半面レイアウト耐性**（比率縮小／左グラフ+右コメントでも読めるか。フルサイズ合格だけで逃げるな）
4. **境界リスク**（Decision/Spec を巻き込むか、Renderer だけで閉じるか）
5. **偽陽性リスク**（データが無いのに意味を描いて嘘になるか）
6. **最小実装**（GO の場合のみ。UI 追加は書くな）
7. **やらないこと**（明示）

禁止回答:

- 「とりあえず両方やる」
- 「AIで自動判定」
- 「ユーザーに色を選ばせるUI」

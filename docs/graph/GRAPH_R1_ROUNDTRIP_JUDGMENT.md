# SUGUDASU Graph — 貼付後手戻り：解法の裁定

**Date:** 2026-08-10  
**Roles:** System Architect · Senior UI/UX  
**Question:** 軸単位・文字が小さい → Graph に戻って直して再コピペが現実解か。他解はあるか。

---

## 一行裁定

> **本命は「戻らなくてよいデフォルト」。**  
> 戻るなら **Graph へ戻ってスロット／表示プリセットを変えて再出力** が、編集不可デッキ向けの **唯一の現実解（許容フォールバック）**。  
> PPT内微調整は理想だが一次解にしない。SUGUDASU 内フル編集は作らない。

---

## シナリオ（ユーザーが言っていること）

```text
PPTに貼る → 軸の単位・文字が小さい → Graphに戻る → 直す → またコピペ
```

これは **失敗パス（手戻り）** であり、成功パスではない。  
ただし Slides / PPT2019 のように **貼付後に図を直せない** 世界では、手戻りが起きたときの **救済は再出力しかない**。

---

## 解法カタログ（MECE）と判定

| ID | 解法 | 判定 | 理由 |
|----|------|------|------|
| **S0** | 出力デフォルトがデッキ半面でも読める（字号・余白・単位表示・線幅） | **本命 · GO** | 3分・編集なし・貼付後編集不可と最も整合 |
| **S1** | 貼る前に **配置スロット**（半面左/全面）を1つ選ぶ → その寸法で canvas+字号を描く | **GO（Presentation Settings 最小）** | Editorではない。手戻り原因の大半（縮小）を先に潰す |
| **S2** | 貼る前に **半面縮小プレビュー**（スライド風フレーム）で可読性を確認 | **GO-AFTER（強い推奨）** | 手戻りを「貼った後」から「出す前」に前倒し。コピー前ゲート |
| **S3** | 気づいたら Graph に戻り、スロット/プリセット変更 → 再コピペ | **許容フォールバック · 現実解** | 編集不可経路ではこれ以外に救えない。成功条件には数えない |
| **S4** | PPT/Keynote 上で字号・単位を微調整 | **二次 · 環境依存** | 理想UX。Slides・PPT2019 SVGでは不可。合否に使わない |
| **S5** | SUGUDASU 内の字号スライダー・軸編集UI | **REJECT** | Graph Editor 化。Pain の再実装 |
| **S6** | EMF/ネイティブチャート等で「必ずPPT編集可」を保証 | **HOLD（将来・別判断）** | 実装コスト大。POC-006 と衝突しうる。今の R1 必須ではない |
| **S7** | Continue Later / JSON で下書き保存し色を後で直す | **主解 REJECT** | 可読性不足は保存では解けない。再出力の補助にはなりうるが今は主題外 |
| **S8** | 複数サイズを一括出力（半面+全面）して選び直すだけ | **GO-AFTER 候補** | 再ペーストは残るが「設定いじり」より速い。UI増は最小に |

## Architect 判定

### 境界

```text
Decision / Spec     … 何を描くか（単位の意味はここ）
Presentation slot   … どの枠に貼るか（半面/全面）
Renderer            … その枠で読める字号・余白で描く
Deck (PPT等)        … 配置・コメント。図の中身の編集は期待しない
```

単位系が「小さい」のは多くの場合:

1. **字号が細い**（Presentation / Renderer デフォルト）
2. **単位ラベルが図に出ていない**（Spec/Renderer の欠落 — 要確認）
3. **縮小で相対的に消える**（スロット未設定）

「単位の意味をユーザーが軸上で打ち直す」は Decision 境界を壊すので **S5 でやらない**。  
単位が出ていないなら **S0 で必ず出す**（編集ではなく完成品の欠落）。

### 手戻りループの位置づけ

```text
成功:  Excel → Graph →（スロット）→ プレビューで読む → コピー → デッキで完了
失敗:  … → デッキで「小さい」→ Graphへ戻る → スロット/デフォルト変更 → 再コピー
```

失敗パスは **消えない**（人間の資料は毎回違う）。  
設計目標は **失敗パスの頻度を下げる** ことであり、失敗パスを高機能エディタで快適にすることではない。

## Senior UI/UX 判定

| 原則 | 適用 |
|------|------|
| ユーザーはグラフをデザインしたくない | S5 禁止 |
| ユーザーはスライド上で「ちょっと直したい」 | S4 は認めるが一次にしない |
| 「小さい」は貼ってから気づきやすい | **S2 プレビュー**が感情コストを最も下げる |
| 戻る操作は怒りのコストが高い | 戻るなら **1操作で再出力**（スロット切替のみ）。細かいスライダー地獄にしない |
| 3分予算 | 手戻り1回までがギリギリ。2回以上はデフォルト失敗 |

### 「戻ってコピペ」は現実解か？

**はい — ただし「編集不可デッキ向けの唯一の救済」として。**  
「それが普通のワークフローです」と製品が言うのは **No**。

ユーザー向けに言ってよいこと:

> だいたいそのままで貼れます。  
> もし小さければ、貼る前のプレビューか、配置（半面/全面）を変えて出し直してください。

言ってはいけないこと:

> いったん貼って、気に入らなければアプリで細かく直して何度も貼り直すのが基本です。

## 推奨スタック（優先順）

1. **S0** デッキ半面でも読めるデフォルト（字号・単位・余白）— 今すぐ品質として攻める  
2. **S1** スロット（デフォルト: 右コメント半面。`proj_safe` は opt-in・一般化保留）— **PPT寸法の事前把握**  
3. **S2** 半面+コメント余白のプレビュー — コピー前に気づかせる  
4. デッキで配置・コメント・会場余白（レイアウト微調整）— **正常作業**  
5. **S3** 内部可読性がダメなら戻ってスロット変更→再出力 — フォールバック  
6. **S4** 環境が許せばデッキ側で内部微調整 — ボーナス  
7. **S5/S6/S7** · PPT寸法の数値入力 · 余白スライダー · Graph内コメントUI — 今はやらない / REJECT  

---

## POC-007 との整合メモ

Constitution POC-007 に「必要なら色・線・表示の微調整」とある。  
本裁定ではそれを **スロット／最小 Presentation Settings** に読み替え、**自由なグラフ編集UIには拡大しない**。

## 追記 — PPT寸法の事前入力 vs コメント vs 微調整（2026-08-10）

**Question:** 事前にPPTサイズを把握／入力させた方が手戻りが少ないのでは？  
コメントも入れたくなるし、やっぱりPPT上の微調整が必要では？

### 一行

> **寸法の「数値入力」はしない。配置スロット（半面／全面など）で把握する。**  
> **コメントはデッキ側が本業。** それは必要な「微調整」だが、**グラフ内部の字号いじりとは別物**。

### 「事前にPPTサイズを入力」は自然に見えるが落とし穴

| やり方 | 判定 | 理由 |
|--------|------|------|
| 幅×高さの px / cm を手入力 | **REJECT（一次UX）** | ユーザーは知らない・測らない。16:9/4:3/ワイド差で混乱。3分を食う。コメント余白まで数値化できない |
| アスペクトだけ選ぶ（16:9 / 4:3） | **GO-AFTER 候補（任意）** | 低コスト。必須にしない |
| **配置スロット**（全面 / 左半分・右コメント想定 / など） | **GO · 本命の「事前把握」** | 「サイズ」ではなく **使い方**を聞く。コメント前提を内包できる |
| 実ファイル（.pptx）をアップロードして寸法検出 | **REJECT（Browser）** | 重い・権限・Non-Send感覚と衝突しやすい。今の線ではない |

「サイズを事前に知る」こと自体は正しい。  
知る手段は **数値入力ではなくスロット選択**。

デフォルトは **`deck_half_left`（左グラフ・右コメント）寄り** が無難。  
全面グラフは少数派の「見せる1枚」用。

### コメントはどこに書くか

Constitution: グラフSVGにタイトル・長文注釈・プレゼン固有文を原則入れない。

| 内容 | 置き場 |
|------|--------|
| 軸・カテゴリ・単位・必要な目盛 | **Graph 出力（完成品）** |
| 「だから今期はこうする」等のコメント・矢印・強調枠 | **PPT/Slides 上（デッキ作業）** |
| グラフタイトル | デッキ側が基本（資料の話の一部） |

コメントを入れたくなるのは正常。  
それは **Graph にコメント編集UIを作れ** ではなく、**右半分を空けるスロットで出し、デッキで書く**。

### 「PPT上の微調整」を2つに分解せよ（混ぜるな）

| 種類 | 例 | 必要？ | SUGUDASUの答え |
|------|-----|--------|----------------|
| **L — レイアウト微調整** | 図を少し動かす、縮小、右にコメントを書く、枠を揃える | **ほぼ常に必要**（資料作りの本体） | **デッキの仕事として歓迎**。Graphは邪魔しない |
| **I — 内部微調整** | 軸字号、単位の出し方、棒の色、目盛密度 | **稀であるべき** | デフォルト+スロットで潰す。不可なら戻って再出力。Editor化しない |

ユーザーが「やっぱり微調整が必要」と感じるとき、多くは **L（コメント・配置）** の話。  
**L はPPTでやるのが正解**であり、Graphの失敗ではない。

**I が頻発する**ならデフォルト失敗（S0/S1/S2を直せ）。  
**I を快適にするためにEditorを足す**のは誤り。

### 成功フロー（コメントあり）

```text
Excel → Graph
  → スロット「左半分・右コメント」
  → 半面プレビューで軸・単位が読めることを確認
  → コピー
  → PPT: 左に貼る / 右にコメントを書く（＝レイアウト微調整 L）
  → 完了
```

内部字号のために Graph へ戻る（I の手戻り）は、ここまでやっても足りないときだけの例外。

### 追記 — image-trim 型プリセットはよいか（2026-08-10）

参照: [画像切り出し（出力サイズ）](https://sugudasu.com/image-trim)  
社内実装: `assets/image-trim-app.js` の `PRESETS`（カテゴリ SNS / 書類・仕事 / Web）

質問者:

> image-trim がよいのかも。通常のプレゼンサイズは PPT・Slides などで決まっているだろう。

#### 一行

> **UI型（カテゴリ＋用途プリセット）は借りる。中身は「切り出し枠」ではなく「デッキ配置スロット」にする。**  
> 数値カスタムは一次にしない。半面コメント前提をデフォルトに足す。

#### 何がよいか（採用）

| image-trim の型 | Graph への転用 |
|-----------------|----------------|
| 「用途名」で選ぶ（Instagram 1:1、社内共有 16:9…） | **GO** — 「1920×1080を入力」より自然 |
| カテゴリで絞る | **GO（薄い）** — Graph は最初から **資料・デッキ** に絞ってよい（SNS列は不要） |
| スライド寸法は業界でだいたい決まっている | **YES** — 16:9 ワイドが主、4:3 は残党 |

書類・仕事の既存プリセット（参考）:

- 社内共有 16:9（1280×720）
- 資料貼り 4:3（1600×1200）
- A4縦（印刷寄り · Graph一次には薄い）

#### 何をそのままコピーしてはいけないか（Diverge）

| image-trim | Graph |
|------------|-------|
| JTBD: **既存画像を枠ちょうどに切り出す** | JTBD: **表からグラフを描き、デッキに貼る** |
| 出力 = クロップ済みビットマップ | 出力 = SVG/PNG（字号・余白が canvas に束縛される） |
| カスタム px が正当（入稿指定） | カスタム px は **一次REJECT**（3分・知らない） |
| 全面フレームが主 | **コメント右の半面**が実務の主 |

したがって:

- 「1280×720 を選んで全面グラフ」だけだと、前回の **左グラフ・右コメント** 問題が残る
- Graph プリセットは **アスペクト × 占有** の積が必要

#### Graph 向けプリセット案（裁定推奨 · 数値は仮）

カテゴリは実質1つでよい: **資料・デッキ**（image-trim の「書類・仕事」相当）

| id | ラベル案 | 意味 | 既定？ |
|----|----------|------|--------|
| `deck_16x9_half_left` | ワイド半面・右コメント | 16:9 スライドの左約半分。字号は半面前提 | **デフォルト（配布・画面共有向き）** |
| `deck_16x9_full` | ワイド全面 | グラフが主役の1枚 | |
| `deck_16x9_proj_safe` | ワイド・投影セーフ | 下部ブランク候補。登壇机で下端欠け対策（**opt-in · 証拠弱め**） | デフォルトにしない |
| `deck_4x3_half_left` | 4:3 半面・右コメント | 旧資料 | |
| `deck_4x3_full` | 4:3 全面 | 旧資料 | |
| `deck_4x3_proj_safe` | 4:3・投影セーフ | 同上（**opt-in · 証拠弱め**） | デフォルトにしない |

px は内部実装詳細。UIには **「ワイド半面・右にコメント」** / **「投影セーフ（下を空ける）」** のように用途を出し、1280×720 を主役にしない（image-trim より用途優先を強めてよい）。

カスタム（px）: 折りたたみ or 非表示。開発者・特殊入稿向けなら後段。

#### 投影セーフ（下部ブランク）— 2026-08-10 追記

実務知見（**証拠レベル: 弱〜中 · 一般化は保留**）:

> プロジェクタ投影のプレゼンでは、**資料の下部にあえてブランクを作る**ことがある。  
> 会場によっては登壇の段机が邪魔で、投影の下端が見えなくなる。

提供者メモ:

- これは **個人の実体験** であり、コーパス統計ではない
- ただし **プレゼンが上手い人がそうしている場面は複数見ている**（実践知・伝播パターン）
- → 「世の中の標準要件」とはまだ言えない。**デフォルト化・必須化はしない**

含意（製品への入れ方）:

| 点 | 裁定 |
|----|------|
| 全面ぴったりグラフ | 投影登壇では下端欠ける **可能性がある**（確定事実ではない） |
| `proj_safe` プリセット | **任意候補（opt-in）**。あると助かる人がいる、程度 |
| デフォルト | **しない**（画面共有・配布では無駄な余白になりうる） |
| コピーやヘルプでの断定 | 「会場では下が欠けるので必須」と書かない。「投影時は下を空ける人も多い」まで |
| 追加調査 | Acceptance / 実ユーザーで「投影で下が消えた」報告が溜まったら昇格。無ければ薄いまま残すか外す |
| Editorか | いいえ。余白スライダー禁止。opt-in プリセット1つまで |

半面コメント（横）と投影セーフ（縦）は直交。積集合は **需要の実測後**。

**R1 での重み:** Gap A（ラベル切れ）・半面デフォルトより **優先度は明らかに下**。今は設計メモに留め、実装キューに押し上げない（GO-NOW にしない）。

#### Tech Adoption

出力サイズプリセットの **データ表** は image-trim と寄せられる候補だが、JTBDが違うので当面 **Diverge（契約だけ意識）**。  
3プロダクト目で同じ表が要るまで無理に `sg-output-size-presets` 抽出しない（Inventory ルール）。

#### 更新スタックへの差し込み

S1 の具体UIは **image-trim 型（用途チップ）** を踏襲し、中身は上表のデッキスロット。  
「PPTサイズ入力フォーム」ではなく「書類・仕事プリセットの進化形」。

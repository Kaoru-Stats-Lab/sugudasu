## この会議で決めたこと

1. **新規 HTML「画像圧縮」は今は作らない（HOLD）。** 非送信で圧縮できることと、カタログに足すことは別。
2. **「SEOは弱くても SUGUDASU にあるかもを裏切らない」は採用理由にしない。** CASE-2026-009（Hub Value）と同型。
3. **「リサイズがあるから圧縮も」は不成立。** 一括リサイズ自体が CASE-2026-011 の PARK（**2026-11-15** HOW レビュー）。未出荷に未出荷を積まない。
4. **「2MB / メール添付に載せる」JTBD は棄却しない。** 新規ページではなく、既存画像出口の提出プリセットとして **11/15 HOW と同じ案件** で見る。
5. **仮置きに圧縮・クロップを入れない**（CASE-2026-010 / 011 維持）。

## メール添付 · 閉域の立法事実（議論メモ）

- Exchange Online / Gmail 等で **メッセージ全体おおよそ 25MB** で弾かれる Pain は実在する。現場の基本路線はクラウドリンクか公認ファイル転送になりやすい。
- 「閉域＝添付も全部 NG」は一律ではない。多いのは: サイズ上限 · 拡張子拒否 · **外向き添付禁止** · 個人向け転送サービス禁止 · 指定クラウドのみ · 真のオフライン閉域。
- 閉域寄りユーザーの配送: 会社公認置き場のリンク、公認大容量転送、小さくする、分割、USB/社内便、会議で見せるだけ。出口が無い真の閉域ではオンライン転送自体が選択肢にならない。
- 含意: ブラウザ圧縮は **提出条件への適合（前工程）** に限る。Pain の本体が「承認された配送路」なら圧縮だけでは解けない。

## 役員会各 ROLE（要約）

| ROLE | 要点 |
|------|------|
| **CPO** | Hub 期待で GO しない。リサイズと圧縮は課題として違うが、実務は「提出直前の容量」という一ゴール。Squoosh が同型 JTBD を既に満たす。残る差別化は貼り先プリセットのみ。 |
| **CTO** | クライアント完結は F2/F3 に乗る。jSquash 全積みは Squoosh 移植で初回負荷が重い。部品なら `@jsquash/jpeg` 遅延読込 + PNG 減色は UPNG。`browser-image-compression` の maxSizeMB は寸法落としであり「圧縮」ではない。fileslim / Inactive は不採用。既存 `webp-to-jpg` は Canvas `toBlob` 済み。 |
| **CMO** | 「画像 圧縮」SEO は大手に取られている。離脱防止は別 URL ではなく同一出口の次アクション。観測に「画像 圧縮」「2MB 以下」を 11/15 トリガーへ足すのは可。 |
| **HCI** | コーデック名・並列比較は出さない。目標 MB なら何を犠牲にしたか（品質か辺か）を結果に必須。 |
| **認知科学** | 制約は二つでもゴールは一つ。ツール分割は文脈スイッチ。減色は不可逆で OCR の静かな変質と同型。期待への応えはカタログ増ではなく今ある出口。 |
| **シニアUIUX** | ドロップ → 提出プリセット少数 → 容量とプレビュー → 持ち帰り。AVIF/JXL は受け取り側摩擦。仮置きには入れない。 |

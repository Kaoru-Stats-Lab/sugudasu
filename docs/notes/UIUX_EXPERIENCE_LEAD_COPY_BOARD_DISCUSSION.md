## 1. 各立場の討議（今回の論点に限定）

### 1.1 CTO

**賛成する総意側**
- 自由記述のまま増やすのは負債。型を **3〜4種に固定**し、変数（What / Why / Boundary一行 / 誘導リンク）で埋める構造化は必須。
- リードと FAQ は **別アセット**（FAQ は FAQPage JSON-LD、リードは自由文）。「FAQに書いたからリード省略」は SEO・自己選別の両方で損。

**紐付け軸**
- 完了系統だけにマッピングすると、同じ `transform_copy` でも normalize（軽）と group-split（重）が同じ型になり破綻する。
- **推奨:** 第一軸は **複雑度（軽量/重量）**。完了系統は第二軸（完了CTAの文法と混同しない）。
- 実装契約への足し方案: `lead_profile: light | heavy`（または `minimal | scenario | boundary`）を `UIUX_DECISION_BLOCK` に追加。`completion_model` の置換ではない。

**尖り（少数寄り）**
- FAQ 型を「主テンプレ」に寄せすぎると、単純ツールに空FAQが増える。FAQ は **疑問が実在するツールだけ必須**。

### 1.2 CMO

**賛成する総意側**
- **トップ = 価値観訴求**は維持（態度変容）。下層は行動喚起。二層構造は正しい。
- リード欠落は FAQ にしわ寄せ → スキャン層で自己選別できず、ロングテール直答だけが残る。両方必要。

**紐付け軸**
- 複雑度二分類で十分先行できる。完了系統採否を待たなくてよい（検索意図は「請求書 無料」であり Transform-Copy ではない）。

**差別化の置き場**
- 競合名指し（Acrobat 等）は **短い予防線をリードに1句**、詳細は FAQ。文脈なしの FAQ 抜き出しリスクは認めるが、リード無だと誤訪問コストの方が大きい（pdf-fill 型を支持）。
- スバル「スグダス」注意は **尖り①** — 露出増は炎上防止に効くがブランド落ち着きを削る。今回は **Defer**（別アジェンダ）。通常ツールリードに混ぜない。

**尖り**
- invoice 級の機能直答は CV に寄与しうるが、「What ゼロ」はやりすぎ。最低1文の What は削らない（少数意見②＝リード廃止には反対）。

### 1.3 CPO

**賛成する総意側**
- 乱立ではなく **軽量 = 機能直答（What短文）** / **重量 = シナリオ + 非対応宣言** の二分類が実態に合う。
- pdf-fill の「代替ではない」は **期待値ミスマッチ防止**。重量ツール（invoice · fair-draw · pdf-* · group-split）へ展開候補。

**紐付け軸**
- **複雑度を第一軸で採択提案。** 完了系統は CTA/完了体験の軸（既決議 P1）と分離し、リードに無理に1:1しない。
- `product_voice` との関係: `fast_utility` → 多くが軽量、`formal_document` / 一部 `board_planning` / `visual_workbench`（pdf-fill級）→ 重量寄り。ただし voice だけで機械決定は危険（stamp は canvas だが比較的軽）。**人間が DECISION_BLOCK で lead_profile を選ぶ**。

**リード vs FAQ**
- 役割時系列（入口の自己選別 / 通過後の境界）に同意。
- 差別化の「一般ルール」は一本化しない: **予防線1句はリード可、境界の論証は FAQ**。両方に同じ長文を置かない。

**尖り②への反対**
- 単純ツールのリード全廃は「予測可能なサイト文法」を壊す。What 1文はコストに見合う。

### 1.4 シニアUIUX

**賛成する総意側**
- Consistency = 文面同一性ではなく **型の予測可能性**。
- ルール案を採択候補にする:

| 層 | 必須条件 | 置き場 |
|----|----------|--------|
| **What**（何か・誰向け） | **全ツールページ必須**（1〜2文） | リード |
| **Why**（何と違うか / 非代替） | 重量・誤訪問リスクがあるツールのみ | リードに **最大1句**、または FAQ のどちらか（重複禁止） |
| **How**（操作手順） | 複雑ツールのみ | 原則 UI 直下の短い手順 or FAQ。リードに手順を書かない |

- `/invoice` の「リード薄 → 即UI → FAQ」は **軽量〜中重量の合法型**になり得るが、現状は What が欠落しているので **違法**。PC推奨注記の前に What 1文を足せば型として成立。
- リードと FAQ の間に長い「本文説明」を挟むのは原則避ける（役割が中途半端になる）。

**完了系統との関係**
- 完了系統は CTA スロットの話。リード型の主軸にすると情報設計が歪む。同意: 複雑度第一。

### 1.5 認知科学

**賛成する総意側**
- 最初の数ページで学習した「サイト文法」が invoice で裏切られると信頼帰属が落ちる。**予測可能な出し分けルール**があれば、トップ（価値観）とツール（What短文）の差は許容される（レイヤが違うと学習できる）。
- FAQ は Just-in-time。通読強制より負荷が低い。
- リードで作った期待と FAQ の **断定度・語尾を揃える**（「しません」vs「原則しません」の食い違いは信頼を削る）。

**差別化対立への裁定案（決定ではない）**
- 少数①（差別化は全部 FAQ）→ 離脱直前に読まれないリスク。
- 少数②（差別化は全部リード）→ SEO/ロングテールを捨て、リードが騒がしくなる。
- **折衷（討議での暫定総意寄り）:** 誤操作・誤訪問コストが高い差別化だけリードに1句。それ以外の「〜できますか」系は FAQ。

## 2. 討議後の総意（仮 · 未決議）

以下は **5者討議の仮総意**。提督の Keep/Change/Defer 記入までは拘束力なし。

1. **トップ** = 価値観訴求型（現状維持）
2. **ツールページ** = 複雑度で分岐  
   - **軽量:** What 1〜2文 → 即 UI → FAQ（任意〜少）  
   - **重量:** What +（任意）シナリオ1句 + 非代替/境界の予防線1句 → UI → FAQ（境界厚め）
3. **リード = Push（自己選別）/ FAQ = Pull（境界）**。同じ事実の要約と詳細の二重化は可。長文のコピペ二重化は不可。
4. **What は全ツール必須。** リード全廃（尖り②）は採らない。
5. **紐付け第一軸 = 複雑度（軽/重）。** 完了系統は CTA 契約の軸のまま。組み合わせは「完了系統 × 複雑度」の表で後から機械化してよいが、今は複雑度で先行可。
6. **スバル注意・誤訪問ブランド注意**は本議題から切り離し Defer。
7. **一括 rewrite はしない。** 新規ツールは DECISION_BLOCK に `lead_profile` を足してから書く。既存は重量ツールからスポット是正。

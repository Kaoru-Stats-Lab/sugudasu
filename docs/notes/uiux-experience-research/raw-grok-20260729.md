**2. ファイルDnDのデファクト（OS／主要Web）**

- **acceptフィルタ問題**: `<input type="file" accept="...">` は選択ダイアログのフィルタとして機能するが、ドラッグ時のブラウザ側強制フィルタにはならない。dragoverで `dataTransfer.items` の `kind` と `type` を確認し、許可しない場合は `dropEffect = "none"` を設定する。出典: MDN File drag and drop（https://developer.mozilla.org/en-US/docs/Web/API/HTML_Drag_and_Drop_API/File_drag_and_drop）。
- **ドラッグ中の視覚**: drop targetで `dragover` を `preventDefault()` し、`dropEffect` を `"copy"` または `"none"` に設定。OSカーソルが変化。追加でCSSによる枠線・背景ハイライトが一般的。OSからのファイルドラッグでは `dragstart`／`dragend` が発火しない点に注意。出典: 同上MDN、および Drag operations（https://developer.mozilla.org/en-US/docs/Web/API/HTML_Drag_and_Drop_API/Drag_operations）。
- **クリック代替**: ドロップゾーンを `<label>` で実装し、不可視の `<input type="file">` を紐付けるのが標準パターン。DnD不能環境でも同一処理を共有できる。出典: MDN File drag and drop（上記URL）。

**3. 「一時状態の色」と「恒常CTAの色」を分けるべきという主張の根拠**

- Material Design（旧）: 「Elements that appear rarely, such as alerts, should be distinct from other elements and not use your primary color.」出典: https://material.io/archive/guidelines/style/color.html （StateおよびUsing color in your app節）。
- Carbon: Primary buttonは画面に原則1つ。Successは別のステータスカラーとして定義。出典: https://carbondesignsystem.com/components/button/usage および Notificationパターン。
- Nielsen Norman Group: ボタンのstyle（primary/secondary）とstate（enabled/pressed等）を区別し、視覚的強調の階層を維持する。一時フィードバックをprimary色で固定する直接的な禁止文言は未確認。出典: https://www.nngroup.com/articles/button-states-communicate-interaction/。
- 学術論文レベルの「一時状態色と恒常CTA色の厳密分離」を直接支持する一次文献は、今回の調査範囲では**未確認**。

**4. コピー操作のアクセシビリティ上の注意（最大5点）**

1. 成功メッセージは `aria-live="polite"` または `role="status"` で通知し、フォーカスを移動させない（WCAG 4.1.3 Status Messages対応）。出典: MDN aria-live（https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-live）、Sara Soueidanの解説（https://www.sarasoueidan.com/blog/accessible-notifications-with-aria-live-regions-part-1/）。
2. コピーボタンに明示的な accessible name（`aria-label` 等）を付与する。アイコンのみの場合は必須。出典: PatternFly Clipboard copy accessibility（https://www.patternfly.org/components/clipboard-copy/accessibility）。
3. 成功時にツールチップや近接テキストを更新し、スクリーンリーダーが変化を検知できるようにする。出典: PatternFly design guidelines（https://www.patternfly.org/components/clipboard-copy/design-guidelines/）。
4. ライブリージョンはページ初期DOMに空の状態で存在させ、後から内容を注入する。遅延追加は通知漏れの原因になる。出典: Sara Soueidan Part 2（https://www.sarasoueidan.com/blog/accessible-notifications-with-aria-live-regions-part-2/）。
5. クリップボード操作自体の失敗時は明示的に通知する必要がある（成功は文脈から推測される場合もあるが、失敗は通知推奨）。出典: WICG Accessible Notifications草案（https://github.com/WICG/accessible-notifications）。

**5. 調査から見える「総意」と「実は分裂している論点」**

**総意**
- コピー成功は短時間の非ブロッキングフィードバック（Snackbar／Toast／ツールチップ更新）で十分であり、ダイアログや永続バナーは過剰。
- 成功色（多くは緑）と主CTA色は役割を分ける設計が主流。
- DnDは `preventDefault`＋`dropEffect`制御と、クリック代替（label＋input）の併用が標準。
- スクリーンリーダー向けにはフォーカス移動なしの `aria-live="polite"`／`role="status"` が推奨。

**実は分裂している論点**
- 成功時にボタン自体の色を一時的に緑へ変えるか（Grafana実装）、ツールチップ更新のみで済ませるか（PatternFly）。
- 成功フィードバックにセマンティック緑を使うか、中立（暗色背景＋テキスト）に留めるか（Material Snackbarは中立寄り）。
- 表示時間の具体値（2秒前後から最大7秒程度まで幅があり、WCAG 2.2.1との関係で調整可能性が議論される）。
- 一時状態色と恒常CTA色の「厳密分離」を必須とする一次ガイドライン／学術根拠は限定的で、設計システムごとの運用差が大きい。

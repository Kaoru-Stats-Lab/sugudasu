## 0. 事実（Evidence）

### 0.1 憲法 · 判例（妥協しない軸）

| 正本 | 拘束 |
|------|------|
| 存在様式 | 結果を持ち帰り、すぐ元の仕事へ戻る |

## 1. 各立場の討議（リサーチ後）

### 1.1 CTO

**読み取り**
- Primer は状態機械（成功は write 成功後）と live region を仕様化している。SUGUDASU の `sg-copy-feedback.js` は近いが、**全面 flash とボタン emerald** が契約と業界の両方から外れ球。
- nodejs.org がグローバル Toast を捨てたのは「バンドル」だけでなく **locus of attention**。我々の P0 toast 乱立は、成功と失敗を同じ箱に詰めた負債。

**見解**
- Copy-First を機械で守るなら、成功プロファイルを **必須**にする: `point_confirm`（ラベル/✓）+ 該当時 `payload_confirm`（行数・先頭行）。「任意トースト」は廃止。
- グローバル成功 Toast・`sg-copy-flash`・ボタン背景の印刷緑流用は **契約禁止**。
- 失敗は別 tone の近接 status（維持）。沈黙失敗は Primer と同じく禁止。

**推奨:** 案 **C+** を `sg-copy-feedback` の唯一の成功パスに固定。

---

### 1.2 CMO

**読み取り**
- Stripe が APIキーで確認を厚くするのは「持ち帰りの失敗コスト」が高いから。帳票の送付文面・共有URLは同じクラス。GitHub のブランチ名コピーと同じ薄さに揃えると、**Copy-First の主CTAが貧弱に見える**。
- 全面緑フラッシュは「気持ちいい」ではなく広告的成功演出に見え、存在様式（すぐ帰る）と反する。

**見解**
- 気持ちよさのマーケ表現: **「押した瞬間、手元に渡った」**。演出予算は全部そこへ。
- 文言は日本語「コピーしました」固定（英語 Copied はブランド・判例周辺でも退行）。
- 行数プレビューはサポートコスト（貼りズレ苦情）削減装置でもある → Transform では必須寄り。

**推奨:** 確認を薄くする Toastレス全面化は **Reject**。派手 flash も Reject。近接の確信を厚くする。

---

### 1.3 CPO

**読み取り**
- CASE-2026-007 の合憲残（コピー主CTA）と F5 を満たす体験品質が、本議題の成功条件。色トークン整理は手段。
- 業界「軽いコピー」ベストプラクティスをそのまま全ツールに貼ると、normalize / report の Oops ガード（§3.8）を捨てることになり **製品差分を捨てる**。

**見解**
- 完了系統で厚みを変えるのは正当:
  - `transform_copy`: 操作点確認 **+** ペイロード確認（行数/プレビュー/フィルター）
  - `print_finish` の URL/文面コピー: 操作点確認（文言+✓）で十分
  - `canvas_copy`: 操作点 or 対象範囲フラッシュ（Figma型）· 全面 flash 禁止
- 「Toast」という語が紛らわしい。正称は **近接ステータス**。Material Snack は採用しない。

**推奨:** 仮総意を **C+** に更新。Gemini T案は「ペイロード確認なし」のときだけ例外表。

---

### 1.4 シニアUIUXデザイナー

**読み取り**
- 業界の「delight」はマイクロインタラクション（1.5–2.5s の✓）であり、ページ染色ではない。
- Primer: success 色は **check アイコン**。ボタンは役割を保つ。現状の `sg-copy-btn--done` 全面塗りは「成功した印刷ボタン」に見えるアンチパターン。
- 近接ステータスのタイポは短く、成功は 2s 前後、警告はより長く or 手動で消せる（Friedman: 重要情報を消えるToastだけにしない）。

**見解 — 気持ちよい仕様の骨格**
1. 押下点: ラベル →「コピーしました」and/or アイコン→✓（success アクセント · **印刷 emerald と別トークン推奨**）
2. 直下: 必要なら `出力 N 行 · 先頭: …`（ハイステークス）
3. `aria-live="polite"`（可視テキストと同期）
4. 全面 flash なし · グローバル Snack なし · 青ボタンは青のまま

**推奨:** DESIGN §3.8 C を上記4点に書き換える。現状 A は「分かりやすいが美しくない・危険」。

---

### 1.5 認知科学者

**読み取り**
- クリップボードは不可視成果物。確認チャネルを削ると不確実性が残り、**再コピー・アプリ切替確認**が増え、持ち帰り（憲法の目的）が遅れる。
- 視線外 Toast は検出率が落ち、安心を買ったつもりで不安が残る（nodejs.org の問題設定と同じ）。
- 全面フラッシュは空間的注意を拡散させ、「何がコピーされたか」の符号化を助けない。Figma の範囲フラッシュは **対象の境界**を教えるので別物。
- 印刷緑でのボタン一時化は、成功の瞬間記憶が「緑=進め/出せ」スキーマに混線する（役割干渉）。

**見解**
- Copy-First 非妥協の認知的翻訳: **確認の情報量を落とすな。確認の空間的散らばりを落とせ。**
- 最良: 操作点の形+言語（二重符号化）+ 必要ならペイロード要約（作業記憶の外部化）。
- 「気持ちよさ」は予測誤差の急速な解消（押した→渡った）。予測誤差を音や全画面色で殴る必要はない。

**推奨:** C+。T案の✓のみは熟練者には十分だが、帳票初見・現場マルチタスクでは言語を残す。

## 2. 総意（仮 · リサーチ後更新）と尖り

| 区分 | 内容 |
|------|------|
| **仮総意** | **案 C+**: 操作点で✓/「コピーしました」（青ボタン維持）· Transform は近接ペイロード確認 · 失敗 status 維持 |
| **仮総意** | グローバル成功 Toast **禁止** · `body` 全面 flash **廃止** · ボタン印刷緑一時化 **廃止** |
| **仮総意** | Copy-First のため確認を薄くしない。削るのは派手さだけ |

| **尖り N** | Material Snack — 色は中立だが視線外 · 採用しない |
| **尖り A** | 現状維持 — 確信は強いが印刷緑衝突・Calm・業界慣行で不採択寄り |

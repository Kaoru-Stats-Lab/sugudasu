# 0. 要約

今回の検討対象は、

> **手元の写真を、提出先が指定する容量または長辺条件に合わせ、そのまま提出できる状態にする**

という単一 JTBD。

これは「画像圧縮」という一般カテゴリではない。

中心となる問いは、

> **提出先の条件に入れる、という独立した3分程度の実務タスクが存在し、既存手段より低い認知負荷で解決する薄い1画面を SUGUDASU に置く価値があるか**

である。

現在の判定は **Park**。

ただし、Park の理由は「アルゴリズム実装が難しいから」ではない。

現時点で最も重要な未解決点は、

> **この JTBD が、実際のユーザー行動として十分に独立しており、かつ既存代替では十分に解決されていないことが証明できているか**

である。

# 1. SUGUDASU の前提

## 1-1. Core

- 登録不要
- 業務データ非送信
- ブラウザ完結
- 静的配信
- 1 Pain = 1 URL
- 3分程度で終わる実務タスク
- Direct / ブックマークは再訪の器
- Hub は「あるかも」で新規 GO しない
- 「困ったらまず SUGUDASU」はカタログ増加の根拠にしない
- 憲法適合を差別化理由と呼ばない

## 1-2. 製品思想上の重要な境界

SUGUDASU は、

- 汎用ツールを何でも集めること
- 大手サービスのクローンを増やすこと
- 「あると便利」な機能を積むこと

を目的にしない。

「必要な瞬間だけ使い、持ち帰る」存在様式と矛盾するような機能肥大化を避ける。

# 2. 今回の JTBD

## LOCKED

JTBD は一件だけ。

> **提出・添付・フォームの容量または長辺に、手元の画像を載せる**

言い換えるなら、

> **提出先が指定するファイル条件を満たす画像を、手元だけで作る**

である。

重要なのは「画像を圧縮する」ことではない。

成功条件は、

- 圧縮率を最適化すること
- ファイルサイズを最小化すること
- コーデックを比較すること

ではなく、

> **提出先に受け付けてもらえる状態にすること**

である。

# 3. ここまでの議論で明確になったこと

## 3-1. Squoosh クローンは作らない

### Reject

以下はすべて Reject。

- Squoosh クローン
- コーデック比較 UI
- 品質スライダー
- 圧縮ラボ
- JPEG / PNG / WebP の圧縮率を試す UI
- Squoosh にない機能を付け足して総合画像圧縮サイト化すること

理由：

> 主座が「提出条件に載せる」から「圧縮を調整する」に変質するため。

さらに、

> 「一般ユーザーは Squoosh を知らない」
> 「SUGUDASU に圧縮があった方が便利」
> 「Squoosh にない機能がある」

は採用理由にしない。

これは CASE-2026-009 と同じ問題で、

> **相手の欠落は立法事実ではない。**

競合がやらないこと自体は GO 根拠にならない。

# 4. 既存ツールへの機能追加

以下は 2026-08-16 時点で確定 Reject。

| 案 | 判定 | 理由 |
|---|---|---|
| `webp-to-jpg` に提出プリセットを足す | Reject | 主座が「形式変換」から「提出条件適合」へ変質する。一般はローカルに WebP を持たない |
| `image-trim` に長辺 / 容量出口を足す | Reject | 「切る仕事」と「提出条件に載せる仕事」が混ざる。仮置き（`clip-stash`）とは別物 |
| `annotate` の書き出しに提出サイズを足す | Reject | 赤入れツールの出口として意味が異なる |
| existing next-path のみ | Reject | 導線は作れても JTBD 本体を解決しない |
| 共通圧縮エンジンだけ先行 | Reject | URL / JTBD 未確定の先行投資になる |

つまり、

> **既存ツールへの機能追加は不適。**

独立 JTBD として成立するなら、新規の薄い1画面しか候補にならない。

ただし現在は ID を切らない。

> 注: `image-trim` を仮置きと同一視しない。仮置きへのリサイズ禁止は CASE-2026-010 / 011（`clip-stash`）。image-trim を落とす理由は JTBD 混線である。

# 7. 形式別の既決

「圧縮」という一つの穴としてまとめない。

## JPEG / PNG

- 提出条件適合の対象
- 11/15 まで Park
- 今回の本命

## GIF

- 「動画を短く動かす / 軽くする」は別の仕事
- コマ抜きは PNG まで
- GIF 化しない
- 今期の提出サイズ HOW でも GIF 非対応
- アニメーション保持を前提にしない

## SVG

- コードを削って軽量化する仕事
- `svg-opt` は vibe PARK
- Hub 増・レッドオーシャン化を避ける

## PDF

- 単体 PDF 圧縮は当面作らない（クライアント圧縮率でブランド毀損リスク）
- PDF 圧縮を今回の画像提出 JTBD に混ぜない

## pdf-images

- 埋め込み画像抽出
- 圧縮ではない
- 今回の候補とは別物

# 8. 「メール 25MB」の位置づけ

メール添付容量制限は、この Pain の一例。

ただし、

> **「25MB 制限がある」＝「画像を圧縮する必要がある」**

ではない。

Gmail / Outlook 等には、製品として

- Drive / OneDrive 等へのリンク化
- 共有ファイルへの迂回

がある。

ただし、**代替が画面にあることと、その人が使えることは別**である（§9 の OS 標準と同型）。

使えるかはユーザー／組織に依る。未検証の仮説として、例えば:

- 会社が指定クラウド以外を禁じている
- 無料枠が足りない（例: OneDrive 無料 5GB に対する忌避。人数の多さは未証明）
- Google Drive は受け入れやすい、という印象がある（印象であり、一次情報ではない）
- 相手がリンクを開けない・ダウンロードを要求する
- 閉域・外向き添付禁止で、リンク化自体が選択肢にならない

したがって、

> **メール 25MB そのものを本命市場とみなさない。**
>
> **メーラーのリンク化が万人の代替である、ともみなさない。**

今回の本命はむしろ、

> **リンク化できない固定ファイルアップロード**

である。

例：

- Web フォーム
- 電子申請
- 応募フォーム
- 業務システム
- ファイル添付欄

など。

# 9. 「OS 標準機能でできる」問題

ここは重要な議論。

## 9-1. 機能の存在と代替の成立は別

OS 標準には、

- 画像のピクセルサイズ変更
- 品質調整
- 書き出し

などの機能がある。

しかし、

> **「2MB 以下にしてください」**

という提出条件を直接指定して、

> **一発で 2MB 以下にする**

という JTBD を OS 標準が必ず提供しているわけではない。

特に重要なのは、

> **「OS に機能があるか」ではなく、「一般ユーザーがそれをこの問題の解決策として知っていて、自力で発見・実行できるか」**

である。

## 9-2. 現時点の整理

「OS 標準でできるから SUGUDASU 不要」

とはまだ言えない。

ただし、

> 「一般ユーザーが OS 標準機能を知らない」

も証明された事実ではない。

したがって今後も、

- 機能の存在
- 発見性
- 想起可能性
- 実際の利用行動

を分離して扱う。

# 10. ユーザー行動に関する現在の仮説

提出条件に遭遇したユーザーは、実際には以下のような代替を使う可能性がある。

- OS 標準リサイズ
- 写真アプリ
- スクリーンショット
- ZIP
- Squoosh
- TinyPNG / TinyJPG
- ILoveIMG 等
- Drive / OneDrive
- メーラーの自動縮小
- LINE / Slack 等を経由した再保存
- 他人にやってもらう
- 別チャネルへ逃げる
- 何もせず提出を諦める

ただし、**これらは現時点では仮説。**

今後は、

> 「ユーザーが実際に何をしているか」

を一次情報・実ユーザー投稿・Q&A 等で確認する。

# 11. 「非送信」の位置づけ

非送信は SUGUDASU の憲法。

しかし、

> **非送信だから需要がある**

とはしない。

検証対象は、

> ユーザーが実際にオンライン圧縮サービスへのアップロードを避けているか

である。

必要なのは、

- 機密データだから嫌
- 規程で禁止
- 外部サーバーに置きたくない

などの一般論ではなく、

> **そのためにローカル処理を探している**

という実際の行動証拠。

# 12. Squoosh との根本的な違い

この議論で最も重要なプロダクト差。

| 観点 | Squoosh 型 | 提出条件適合型 |
|---|---|---|
| 主目的 | 画像をどう圧縮するか | 提出条件に入れる |
| 主役 | 画像品質 / コーデック | 提出先の条件 |
| ユーザー判断 | 多い | 少ない |
| 入力 | 品質 / コーデック / サイズ | 条件プリセット |
| 成功条件 | 良い品質で軽くなる | アップロード / 添付できる |
| ユーザーの問い | 「どう小さくする？」 | 「これを通せるサイズにして」 |

この差が、本当にユーザー行動として存在するなら独立 JTBD の根拠になる。

未検証のまま、差があることを事実化しない。

# 13. プリセット仮説

候補として以下を考えている。

- 2MB 以下
- 5MB 以下
- 10MB 以下
- 長辺 1200px
- 長辺 1600px
- 長辺 1920px

ただし、

> **これらを仕様として確定していない。**

確認すべきなのは、

- 実際に制約がこの範囲に集中しているか
- 容量と長辺が同時指定されるか
- 形式まで指定されるか
- 1枚制約か合計制約か
- 非標準値が多いか
- 自由入力が必要になるか

である。

特に、

> **「少数プリセットで大半を救える」**

という 80% 等の数字は未検証。

精密な数値を作らない。

HOW 草案の `mail_attach` / `form_2mb` / `web_long_edge` も一次案であり、本記録で確定しない。

# 14. 技術的成立性の整理

## 実装可能性

ブラウザ内で、

- Canvas
- Canvas `toBlob`
- WASM
- JPEG / PNG 変換
- 長辺リサイズ
- quality 調整
- 二分探索

などを組み合わせることは技術的には可能。

したがって、

> **「技術的に作れない」ことが Park 理由ではない。**

## 本当の技術・製品論点

重要なのは、

> **「容量以下にする」こと**

と

> **「品質を壊さず提出できること」**

は別問題であること。

特に、

- 身分証
- 領収書
- 工事黒板
- 現場写真

などでは、

- 文字
- 印鑑
- 数字
- 輪郭

の視認性が重要になる可能性がある。

しかしこれを理由に、

- SSIM
- OCR
- 複雑な画質判定
- EXIF 完全管理

などを即座に仕様化しない。

それらは「本当に必要か」を検証してから考える。

# 15. 失敗モード

候補として認識しているもの：

1. 容量は減ったが文字が読めない
2. 顔や証跡が粗くなる
3. 長辺を縮めすぎる
4. 形式が提出先に合わない
5. 複数枚合計で容量超過
6. EXIF が消える
7. GPS が残る
8. 「容量以下なのに」提出先に弾かれる
9. 大きすぎる画像でブラウザが不安定
10. UI を守るために条件を単純化しすぎて使えない

ただし、

> **これらは「すべて解決してから GO」ではない。**

まず「この JTBD が独立価値を持つか」を判断する。

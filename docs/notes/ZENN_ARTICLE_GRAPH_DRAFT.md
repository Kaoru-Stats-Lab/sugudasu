### 本文

データを Excel やスプレッドシートにまとめていると、部署や会社によって「グラフをいつ作るか」の空気がかなり違います。

テーブル（Raw data）だけで仕事が回る文化にいたころは、グラフが必要になるのは主に全社発表のときでした。そのときは、部署の Excel に詳しい方が、会社の CI / VI に沿ったきれいな図を、短時間で整えてくださることが多かった。個人が毎回グラフ職を抱える前提ではなかった、という感覚です。

一方で、プレゼン資料の完成度が強く求められる部署や会社に身を置くと、否応なく Excel やスプレッドシートでグラフを作る場面が増えます。個人的には「表を見れば分かるのに」と感じるギャップもありました。もちろん、伝えたい相手や場によっては、グラフにした方が分かりやすい。それは否定しません。ただ、Excel でグラフを作る経験が少ない人にとっては、想像以上に時間がかかります。PowerPoint のドラフトを七〜八割まで仕上げても、最後のグラフで足踏みする——そんな経験は、自分にも、周囲にもありました。「グラフを作るのは苦手」という人は、あなたの職場にも少なくないのではないでしょうか。

最近の AI に頼んでも、グラフまわりは苦戦している印象があります。形は出ても、意図とずれたり、根拠の薄い見た目になったりする。いわゆるハルシネーションのリスクも、資料に載せる図では重いです。

もうひとつ、出発点があります。人や媒体によっては、意図的・半ば無自覚に、読み手を誤導するグラフ——いわゆる「グラフ詐欺」——が残ります。テレビや新聞などのオールドメディアに限らず、ネット上でもよく見ます。分かりやすさの道具が、信頼を削る道具にもなりうる。**なんとかせねば**、という感覚が、SUGUDASU Graph（仮称）の設計の手前にあります。

成功条件は、描画エンジンの自慢ではありません。

> Excel からコピーし、意図を選び、必要なら最小限の表示調整をして、**おおよそ3分以内にプレゼンへ貼れる**図を出す。  
> **ユーザーに、グラフ編集そのものを仕事にさせない。**

そのまま資料に貼れる八十〜九十点。百点の編集可能性ではありません。この記事は、そのために判断系をどう閉じたかのメモです。公開UIの操作説明ではありません（いまは Output Acceptance＝貼付検証の段階です）。

## 困っていることの芯

本質は「描けない」ことより、次に近いことが多い、と考えています。

> 何を伝えたいかに対して、どの表現形式が適切かを決められない。  
> 決められても、Excel の操作に時間が吸われる。  
> 決めたつもりでも、軸や比較の取り方で誤導しうる。

肩代わりしたいのは Excel の描画機能そのものではなく、**作法の選択**と、**編集作業への引きずり込みを止めること**です。種類のドロップダウンと色パネルを足すと、利用者は Excel のグラフウィザードに引き戻され、3分で資料に貼るどころではなくなります。

## 意図と作法——学習の機会が少ない、という前提

もうひとつ、このプロダクトに強くある意図があります。

大学や現場では、「推移を強調したいなら折れ線」「カテゴリの大小なら棒」のような作法が、講義・先輩・上司・同僚から口伝で渡ることがあります。一方で、その機会に恵まれない人も少なくありません。Excel の「おすすめグラフ」は便利ですが、**自分が何を伝えたいか**から入る学習にはなりにくいことがあります。結果として、図はできているのに、読み手に意図が届かない——いわゆる「伝わらない」——が起きます。

Graph は、その作法をプログラムとして肩代わりし、**伝わらないことを防ぐ**方向にも倒しています。種類名を選ばせるのではなく、「何を伝えたいか」（Intent）から入り、データが許す表現へ落とす。できれば、なぜその形になったかも、あとから説明できる形で残す（説明文を LLM に委ねない）。

具体例です（現場でありがちなズレのイメージです。実装の全分岐表ではありません）。

| 伝えたいこと（Intent） | 表のイメージ | ズレやすい選び方 | 起きやすい「伝わらない」 |
|------------------------|--------------|------------------|---------------------------|
| 年ごとの売上の**推移**を見せたい | 年度 × 金額 | 円グラフや、カテゴリ棒のまま並べる | 「変化」より「内訳」や「並び」に見える |
| 部署間の売上を**比較**したい | 部署名 × 金額 | 折れ線で結ぶ | 部署に時間順がないのに「流れ」があるように読まれる |
| 構成比・**割合**を伝えたい | 部分と全体 | 軸の取り方や積み上げの扱いを誤る | 合計が 100% に見えない／比較に見える |
| **順位**を見せたい | 店舗 × 件数など | 時系列風の折れ線や、順不同の棒 | 「何位か」より「いつ増えたか」に読まれる |
| 二つの数値の**関係**を見たい | 広告費 × 成約など | 無理に棒や折れ線だけに落とす | 相関の話なのに、時期比較や内訳に見える |

大事なのは、きれいな図を量産することより、**意図と表現がすれ違ったまま資料に載るのを減らす**ことです。詐欺（誤導）への違和と隣り合っていて、無自覚なすれ違いも「伝わらない」の一種だ、という位置づけです。

## タイトル · 凡例 · 軸——「種別が合っていても」伝わらない

種別の選択だけが作法ではありません。実務では、次のような欠落や過剰でも「伝わらない」が起きます。

| 要素 | ありがちな状態 | 読み手に起きやすいこと |
|------|----------------|------------------------|
| **タイトル** | 無い／表のシート名のまま／スライド見出しと二重 | 何の図か分からない、または説明が重複してうるさい |
| **凡例** | 単系列なのに常時出す／多系列なのに無い／色と対応が弱い | 「どれが何系列か」で止まる。単系列では余白だけ食う |
| **軸ラベル · 単位** | 単位が無い／千円と円が混ざる／軸が何を示すか不明 | 大小の印象だけ残り、比較の意味が崩れる |
| **カテゴリラベル** | 長い部署名が切れる／重なる | 比較対象が読めず、貼った時点で未完成に見える |
| **データラベル** | 全部に数値を載せて潰れる／必要な箇所だけ欲しい | 読めない、または棒の比較がかえって難しくなる |

Excel ではこれらを個別にいじれるぶん、経験が少ない人ほど「どこまで直すか」で時間が溶けます。逆に、見た目だけ整えて単位や凡例が曖昧なまま出すと、先に触れた誤導（グラフ詐欺）の入り口にもなりえます。

Graph 側の方針は、ざっくり次です。

1. **意味が成立するのに必要な文字**（軸・カテゴリ・単位・必要な凡例など）は、図の一部としてきちんと出す。貼ったあと Google スライドや PowerPoint で SVG を直せない現場がある前提なので、「あとで直せばよい」を一般解にしない。  
2. **資料固有の文**（プレゼン用のキャッチーなタイトル、出典の長文、注釈）は、原則としてスライド側に任せる。図の中に何でも書き込むと、編集UIと長文レイアウトの沼に入る。  
3. **凡例は必要なときだけ**。単系列で色の対応が自明なら、出さない選択も含めてデフォルト品質の問題とする。  
4. **タイトルや凡例の自由編集UIは持たない**（R1）。色・線幅・凡例位置・軸文言のエディタは、3分貼付から簡易 Illustrator への逸脱だから禁止に近い。欲しい微調整は、将来も少数の Presentation Settings（表示のオンオフや単位表示など）に閉じる想定で、Decision（どのグラフか）とは分ける。

つまり「伝わらないを防ぐ」は、Intent×種別だけではなく、**タイトル・凡例・軸・単位の扱いを、編集させずに足りる状態で出す**ことまで含みます。ここが足りないと、せっかく作法が合っていても、貼った瞬間に資料として未完成になります。

## Excelを「DBにすればいい」とは限らない

ここで、少し別の問題を考えます。在庫管理です。

企業の在庫管理表を見ると、「これはデータベースにした方がいい」と思う表がたくさんあります。品番、数量、入庫、出庫、棚、日付……。きれいに正規化して、マスターを作って、ERP や WMS に入れればよさそうに見える。

でも、現場ではそう簡単ではありません。現場の Excel には、システムの都合では表現しにくい情報が大量に入っています。「検収前だけど現場にはある」「このロットは○○工事に仮置き」「返品予定」「A現場からB現場へ転用」「この数字は経理にはまだ渡していない」——といった、人間が運用上必要としている状態です。

日付が横に並び、商品ごとに入庫・出庫・在庫が三段になり、結合セルがあり、前月繰越が別列にあり、得意先でシートが分かれ、月別ファイルになり、ピボットになり、紙の棚卸表も残る。データベースとして見れば、ひどく見えることがあります。しかし、**現場にとっては意味がある**。

だから、Excel を正規化して ERP に移せば問題が解決する、とは限りません。むしろ現場にとっては、

> 「今まで仕事を回していた表を、システムの入力項目に合わせて作り直してください」

という話になってしまう。

ここで私は、Excel を「遅れた IT」とだけ見ることに少し違和感があります。Excel は、ときに**現場の知恵を保持した、非常に雑で柔軟なインターフェース**だからです。いわゆる「汚いデータ」ではなく、**人間が仕事をするために圧縮した帳票**であることが多い。

一般的な DX の物語は、だいたいこうなりがちです。

```text
Excel管理
  → データを整理
  → ERP導入
  → 業務標準化
```

実際には、こうなることも多い。

```text
Excel管理
  → 現場固有の関係・例外・判断ルールが大量に埋め込まれている
  → ERPの標準データモデルに乗らない
  → 「ERP導入したけどExcelがなくならない」
```

つまり Excel は単なる旧式システムではなく、**現場の暗黙知を保存している半構造化の道具**でもあります。在庫管理そのものを SUGUDASU で解こうとしない方がいい、と調査の途中ではっきりしました。SKU マスター、得意先コード統一、入出庫のトランザクション化、棚卸資産の計算——そこは ERP / WMS / 会計の泥沼です。

では、その Excel をどうするか。

> **必ずしも DB 化しなくていい。**

ここがポイントです。Graph は Excel を「正しいデータベース」に変える製品ではありません。Excel に残っている表をそのまま入力として受け取り、その表から観測できる構造を取り出し、ユーザーが伝えたい意図を選び、それに適した表現へ決定論的に変換する。

```text
現場のExcel（帳票のまま）
  → そのまま受け取る（正規化しない）
  → Observable Extraction
  → Intent（推移 / 比較 / 内訳 など）
  → Decision Engine
  → Graph Spec
  → Renderer
  → 資料に貼れる図
```

従来の業務システム思想だと、

```text
Excel → 正規化 → マスター統合 → DB → BI → グラフ
```

となりがちです。Graph は、

```text
Excel → 観測 → 意図 → 表現
```

でいい、と考えています。

この差を一文にすると、こうなります。

> **汚い Excel を綺麗にすることと、そこから正しいグラフを作ることは、別問題である。**

前者に入ると、ETL・データ基盤・ERP の巨大な世界に吸い込まれます。後者は、「その表、DB じゃなくてもいい。まず、会議に貼れる図にしよう」という小さな出口です。3分で仕事を終わらせる、という SUGUDASU の向きとも整合します。

在庫表はあくまで**反例**です。Graph の主題は在庫管理ではありません。同じ構造は、売上管理表、仕入、発注一覧、工事台帳、人員表、予算実績、原価管理——「会社ごと・担当者ごとに形が違う帳票」のあちこちにあります。だからこそ、

> **ユーザーの業務帳票を、正規化されたデータベースへ変換することを目的にしない。**  
> **企業・担当者ごとの構造差を吸収するためのマスター設計や ER 設計を要求しない。**  
> **既存の成果物を、比較・確認・説明可能にすることを優先する。**

という線を、はっきり引きたいです。

余談ですが、隣の道具との境界も、この線の上にあります。「先月と今月で何が変わったか」は Diff の問いです。「どう変化しているか／どう見せると伝わるか」は Graph の問いです。「この数字を会議でどう話すか」は Presentation 寄りの問いです。在庫を管理するのではなく、**在庫を管理している人がすでに持っている成果物を扱う**——その切り方が、Graph にもそのまま乗っています。

## パイプラインを分ける

```text
Observable Extraction
  → Decision Engine
  → Graph Spec Builder
  → Spec Validator
  → Renderer（R1: Bar / Column / Line）
  → SVG / PNG
```

意味を決めるのは **Graph Spec** までです。Renderer は Spec を絵にするだけです。入力を矯正しない方針は、この一段目——Observable Extraction——にすでに現れます。商品マスター上の正しい SKU 名を聞かない。品番の正規化を要求しない。見えている構造と、ユーザーが選んだ Intent だけを見る。

禁止していることの中心は次です。

- Renderer がルールを再判定する  
- Intent や Observable を描画時に再解釈する  
- グラフタイプを勝手に選び直す  
- **`matched_rule_id` で分岐する**（特に禁止）  

「どのルールに当たったか」で描画を分岐したくなるのは自然です。しかしそれは、判断を Renderer に再輸入することです。検証と描画の責任が溶け、回帰が効かなくなります。当たったルールの ID は監査や説明に使えても、**絵を変えるスイッチにしてはいけない**、という線です。

## LLMを置かない

自然言語で「いい感じのグラフ」を任せる道もあります。Graph では LLM を不要・固定としています。理由はシンプルで、提出・資料用の図で欲しいのは再現性です。同じ Observable・同じ Intent なら、同じ Spec に落ちる。モデルのゆらぎで棒が折れ線に化ける世界は、3分貼付の敵です。先に触れた「AIでも苦戦する」「根拠の薄い見た目」への違和とも、同じ向きです。

軽量モデルをブラウザに載せる検討（別文脈）とも同じで、「できそう」より「十分に信頼できるか」を先に見ます。

## IRコーパスで見たこと——と、2軸グラフ

### なぜ IR を参考にしたか

グラフの作法を決めるとき、教科書の理想だけでも、自分の好みだけでも足りません。一方で、社内の生資料を大量に集めるのは、許諾・秘匿・再現性の面で難しいことが多いです。

そこで研究コーパスとして、日本の上場企業が公開する **IR 一次資料**を選びました。理由は単純です。

1. **数字と伝え方がセットになっている**  
   売上・利益率・前年比・セグメント・構成比などが表や数値としてあり、同じ資料の中で棒・折れ線・積み上げ・円／ドーナツ・複合・2軸など「どう見せたか」も見える。  
   つまり «データ構造 → 伝えたいこと → 実際に採用された視覚表現» の実例が、公開物として大量にある。
2. **検証可能性を優先できる**  
   公式一次資料なので、二次まとめや推測分類に頼りにくい。可能な範囲で表・本文・注記と突合し、検証不能なものはコーパスから外す、という運用がしやすい。
3. **製品入力とは切り離せる**  
   製品は IR の PDF を解析してまねるツールではない。入力の基本は Excel / スプレッドシートからの貼り付け。IR は「現場で何が起きているか」を見るための観察源であり、学習データでも正解集でもない。
4. **画像から数値を逆算しない**  
   完成図だけから元表を推測すると、軸の切断・2軸・丸め・単位省略・注記などで不確実が残る。推測しない・同じ入力なら同じ結果、という方針と相性が悪いので、研究方法の主軸にはしない。

こうした位置づけで、決算説明・短信・有報・統合報告書などからグラフ表現を突合したコーパスを **100 ケース**分、検証可能な範囲で集めました。

前節の在庫表と同じく、ここでも「公開されている表現＝推奨」にはしません。IR は観察源です。現場帳票も観察源です。どちらも、入力を正規化しろとは言いません。

### コーパスから見えたこと

ざっくりした傾向の例です。

| 観察 | 目安 |
|------|------|
| 時系列×1指標の推移 → 折れ線 / 短い時系列なら柱 | コーパス上、多いパターン |
| カテゴリ比較・順位 → 棒 | 同様に多い |
| 時間×実数＋別単位（率など）→ 複合 / **2軸** | 条件付き判断が必要な帯（コーパスでも一定数） |
| 構成比で円・ドーナツが実務に出る | 比較精度を優先する推奨では棒側へ倒すことがある |

全体として、企業の実務グラフと、こちらが推奨したい表現が一致するケースと、ずれるケースの両方がありました（おおよそ一致寄りが多い一方、ずれも無視できない割合）。大事なのは次の線です。

> **Observed Graph ≠ Recommended Graph**  
> IR に出ていたから正解、にはしない。

特に **2軸グラフ**は、実務ではよく使われます。「月×売上（実数）×利益率（%）」のように、実数と割合を一つの図で見たい、は現場の典型です。Excel では第2軸・系列の種類・軸の設定・単位・スケールが難しく、時間もかかり、軸の取り方次第では読み手が傾向を誤認しやすい——いわゆる誤導の入り口にもなります。

だから Graph では、2軸を「高度なおまけ機能」扱いにはしません。一方で、データ構造だけから「同時に見る意味がある」まで機械が決め切るのも危険です。いまの設計方針はおおよそ次です。

- デフォルトは認知安全性を優先し、**Small Multiples（分けて見せる）を原則**  
- **2軸はユーザーが明示したとき**を基本にする  
- 採用するなら、両 Y 軸の 0 基線の同期、スケールと軸の意味の明示、勝手な自動スケールの禁止などを制約候補にする  
- 同期できないなら 2軸を捨てて Small Multiples へ倒す  

円・ドーナツも同様で、実務多用でも、カテゴリ比較の精度では棒を優先することがあります。ここも「IR をまねる」のではなく、「IR で何が起きているかを見て、推奨を別に持つ」です。

なお R1 の描画解禁は Bar / Column / Line に閉じます。2軸や複合は、研究と Decision の話として先に抱え、いきなり広く描画解放しない段階です。

### 正直な限界——IR と、想定ペルソナの実務はまだ突合できていない

上に書いたとおり、IR を選んだのは「数字と伝え方がセットで公開されている」「検証しやすい」からです。その強みは残ります。一方で弱みは、読み手が主に投資家・アナリスト向けであることです。社内資料を集めにくい、という事情の裏返しでもあります。

SUGUDASU が想定している利用者は、営業・経営者・経理・管理職・中小企業の担当者など、**毎回デザイナーに頼めない実務者**に近いイメージです。IR で観測した「よくある表現」や「ずれる点」が、その人たちの社内資料・顧客向け資料でも同じ重みを持つかは、**まだ検証できていません**。在庫表のような現場帳票の観察も、いまは思想の補強であって、ペルソナ検証の完了ではありません。IR はエビデンスの一層であって、代替ではありません。

そこで、読者の方にも素直に聞きたいです。

> この種の「IR 由来の観察」と「社内・提案資料の実務」のずれを、どう検証するのがよいでしょうか。

いま頭にある候補は次のようなものです。足りない・危ないものがあれば教えてください。

1. **想定ペルソナへの短いインタビュー**（普段いつグラフを作るか、2軸を使うか、どこで詰まるか）  
2. **紙芝居または低精度プロトタイプ**で、Intent 選択 → 貼付 → 2軸の確認が出たときの反応を見る  
3. **社内資料・提案資料の小さなコーパス**（許諾の取れる範囲）を IR とは別に作り、Observed / Recommended を同じ枠で記録する  
4. **誤認タスク**（同じ表で 2軸と Small Multiples を見せ、読み取った結論のずれを測る）  
5. **ログではなく対話**で、MATCH / MISMATCH /「自分ならこうする」を集める（送信前提のテレメトリに頼らない）

「IR で十分」「IR は参考に留めよ」「検証はこの順序がよい」など、実務・研究どちらの視点でも構いません。コメントや反応で教えてもらえると助かります。

## 「グラフ詐欺」への向き

詐欺を完全に防ぐ魔法はありません。それでも、軸・比較・単位・系列の扱いを、描画時の裁量やモデルの気分に預けないことには意味があります。2軸の自動スケールや、単位の曖昧な重ねも、ここに入ります。決定論のパイプラインは、速さのためだけではありません。**同じ入力なら同じ結論**に落とすことで、あとから説明しやすくし、勝手な美化の余地を狭めるための選択でもあります。

R1 で解禁している表現は Bar / Column / Line に限っています。派手な複合や、読み手を誤導しやすい表現を、いきなり広く解放しない、という段階の取り方でもあります。

## Renderer の範囲

R2 / R3 は HOLD。グラフ種別の追加も、いまは止めます。編集UI（Graph Editor）は禁止です。色・線幅・凡例・軸ラベルの編集パネルも、ここに含みます。欲しくなった編集は、だいたい「Excel に戻った方が速い」領域に入ります。部署に Excel 職人がいる文化では、その方に任せる方が早い場面もある——Graph はその代替宣言ではなく、**職人がいない／自分が苦手なときに、貼れる八十点を出す**ための道具です。

主出力は SVG、必要なら PNG。成功は「描画できた」ではなく、**実務資料に貼れる**ことです。余白・字号・線の太さは、フルブリード前提ではなく、スライド半面に縮小されても読める方へ寄せます。カテゴリ名が切れる・凡例が潰れるのは、編集UI需要ではなく出荷品質の問題、という立て方です。

## コアの「枯れた技術」との関係

抽出や描画の部品は、できるだけ挙動が読めるものに寄せます。新しいのは、AIではなく **判断を閉じたパイプライン**です。ブラウザ完結の制約の中で、編集ソフト化しないための境界、と言ってもよいです。

製品の公開面や名称はこれから詰まります。先に固定したのは Constitution 側——何を成功とし、Renderer に何をさせないか、**入力帳票を正規化しないか**——です。

Excel を捨てなくても、Excel の中にある数字は、資料に載せられる形にできる。正規化はその後でも、やらなくてもよい。その小さな出口を、Graph は取りにいっています。

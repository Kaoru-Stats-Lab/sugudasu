## 1. 解けたい JTBD（一つ）

提出・添付・フォームの **容量または長辺の条件** に、手元の画像を載せる。

| 表面の言葉 | ユーザーのゴール |
|------------|------------------|
| まとめて縮小 | 枚数が多いときの反復摩耗 |
| 圧縮 | 多くの場合「添付できる大きさ」 |
| 2MB 以下 · 25MB 以下 | 提出先のゲート |

リサイズ（寸法）と圧縮（エンコード品質）は技術的に違う。製品上は **提出プリセット** にまとめる（ユーザーにコーデックを選ばせない）。

## 4. UX 上限（HCI）

```
ドロップ（複数可） → 提出プリセット 1 択（最大3） → 結果一覧（容量・辺・犠牲の明示） → まとめて保存
```

プリセット案（ラベルはユーザー語）:

| id | ラベル案 | 裏の意味（出さない） |
|----|----------|----------------------|
| `mail_attach` | メールに付けやすく | 長辺上限 + JPEG quality。目標おおよそ 1〜3MB/枚のオーダー |
| `form_2mb` | フォームの 2MB 以内 | 品質と必要なら長辺を段階的に。**辺を落としたら UI に書く** |
| `web_long_edge` | Web用（長辺1200） | 寸法優先。品質は固定 |

禁止: Quality スライダー常時表示、MozJPEG / OxiPNG の名前、並列コーデック比較。

**受け入れ:** 元を上書きしない。別名 DL。枚数 **20**（§9）。  
**結果一覧（必須）:** 各枚について最終容量・出力寸法・辺を落としたか。処理中のリアルタイム逐次表示は必須にしない（Worker 逐次処理。完了行だけ更新でよい）。  
**容量未達:** 目標（例: 2MB）に届かない枚は「収まりませんでした」系の状態を出す。成功扱いの完了感を出さない（文言は実装時。仕様として状態表示は必須）。  
**短辺指定:** 不採用（今期）。縦長も長辺基準で扱う。Gemini 再提出防止のためここに明記。

## 5. 技術 HOW（部品）

| 段階 | 手段 |
|------|------|
| MVP 候補 | Canvas `toBlob('image/jpeg', q)` + 長辺リサイズ（既存 `webp-to-jpg` 系）。**Web Worker 逐次**（20枚でメインスレッド凍結させない） |
| 出力前（必須） | **EXIF Orientation を正立化**してからリサイズ・エンコード |
| 透過 → JPEG | **白背景 `#FFFFFF` を合成**してから JPEG 化（未定義にしない） |
| メタデータ | 提出用出力から **EXIF（GPS・機種等）を載せない**（再エンコードで落ちる想定を仕様として明記） |
| PNG が大きく残るとき | 別プリセット「色を減らして軽くする」→ UPNG 候補。可逆と混ぜない。プレビュー必須 |
| Canvas で足りないと実測されたとき | `@jsquash/jpeg` を **遅延読込** vendor（pdf.js 型）。全 jSquash 初回積載は禁止 |

OSS 詳細は議論ログ。Tech Adoption: Platform SDK 先作り禁止。体験が揃うために薄い shared を足す。

**観測のみ（今期仕様に入れない）:** ICC/広色域の色ずれ · 複数枚のメール合計容量ゲート · sRGB プロファイルのブラウザ差。

## 8. 競合地図 — Imgix ブログ「一括リサイズ」記事（2026-08-15 突合）

**出典:** [画像の一括リサイズ決定版！おすすめツールや選び方、注意点を解説](https://jpblog.imgix.com/bulk-image-resizing/)（Imgix Blog · 生成AIカテゴリ表記あり · 自社 CDN 誘導あり）

記事の主戦場は **EC / メディアのサイト表示速度 · SEO · 大量画像運用**。SUGUDASU の主戦場は **事務の提出・添付・フォーム直前**。同じ「一括リサイズ」語でも JTBD が違う。

### 8.1 記事にあるもの → 採用 / 非採用 / 加える

| 記事の論点・例 | 判定 | SUGUDASU での扱い |
|----------------|------|-------------------|
| メリット: 表示速度 · SEO · EC 直帰防止 | **非採用（主訴求）** | コアの Persona はサイト速度担当ではない。コピーに SEO/PageSpeed を載せない |
| メリット: 作業効率（何十枚を手でやらない） | **採用（JTBD の一部）** | 「単純反復の摩耗」として HOW §1 に既にある。枚数は数十枚オーダー想定 |
| 種類: Web ブラウザ型 | **採用（形態）** | インストール不可の閉域寄りと一致。ただし **アップロード型は Reject**（F2） |
| 種類: PC ソフト / スマホアプリ / CLI | **非採用** | Domain 外。Photoshop バッチ・Imgix CDN は Outside Scope |
| 選び方: 枚数で選ぶ | **採用（設計制約）** | 上限は新発明せず **既存 MAX_FILES=20** に揃える（§9） |
| 選び方: 用途で選ぶ（EC 統一 / SNS プリセット） | **一部採用** | SNS 固定枠は既に `image-trim`。一括 HOW の主プリセットは **提出・添付・Web長辺**（SNS は混ぜない） |
| 選び方: 画質と容量のバランス · スライダー · 可逆/非可逆切替 | **非採用（UI）** / **採用（結果の明示）** | スライダー常時は禁止（§4）。犠牲（辺・品質）は結果に書く |
| 選び方: インストール可否 | **採用** | 「ブラウザだけ」は差別化の事実。statements 既存。記事の Boost/ILoveIMG は多くが **サーバ送信** |
| おすすめ: Boost Tool / ILoveIMG | **競合として観測** | Web 型だがアップロード前提が多い → 非送信が差別化。機能セットの模倣はしない |
| おすすめ: Photoshop バッチ | **非採用** | 学習・設定・常駐ソフト。Anti |
| おすすめ: Imgix（URL パラメータ · CDN · AI） | **Reject（コア）** | サーバ最適化 · アカウント · F2/F3 と衝突。Sync でも旗艦にしない |
| 注意: 元画像バックアップ | **加える** | 一括は上書き事故が怖い。出力は **別ファイル名で DL**、元は触らない、を受け入れ条件に |
| 注意: 画質劣化 · 形式ごとの特性 | **加える（ユーザー語）** | コーデック名は出さない。「写真が荒れることがある」程度の Boundary 1 句は可 |
| 関連機能: WebP 変換 · PDF 化 · トリミング · アップスケール · クラウド連携 | **非採用（この HOW）** | WebP→JPEG は `webp-to-jpg`、切出しは `image-trim`、PDF は別系統。クラウド連携は Reject |
| AVIF を高圧縮として紹介 | **非採用（主出力）** | 受け取り側摩擦。§2 維持 |

### 8.2 記事から HOW に足すもの（差分）

1. **枚数上限** — **20枚**（`webp-to-jpg` / `watermark` と同一）。詳細 §9。  
2. **元を壊さない** — 上書きしない · 別名 DL · 失敗時も元ファイルは端末のまま。  
3. **競合ポジション一文** — 「アップロードする一括リサイズ」ではなく「ブラウザ内で提出サイズに合わせる」。  
4. **観測キーワード追記** — 記事語彙: 「一括リサイズ」「画像 最適化」「表示速度」は SEO 需要の地図。採用理由にはしないが GSC 観測の参考。

### 8.3 記事が証明しないこと

- Hub に無いと困る、では GO にならない（CASE-009）。  
- サイト速度・SEO を主 Pain にすると、Imgix / 各種アップロード Web ツールの土俵に乗る。  
- 「おすすめ4選」の機能を揃えることは製品要件ではない。

## 9. 枚数上限 · 出力ファイル名（CPO / HCI / シニアUIUX · 2026-08-15）

### 9.1 既存画像系の事実

| ツール | 枚数 | 1ファイル | 出力名の型 |
|--------|------|-----------|------------|
| `webp-to-jpg` | **MAX_FILES = 20** | 25MB · 長辺8192 | `{元stem}.{新ext}`（拡張子だけ） |
| `watermark` | **MAX_FILES = 20** | — | `{stem}_wm_01.png` 等 · `sanitizeBaseName` |
| `image-trim` | **1枚** | 25MB | `{stem}-{W}x{H}.png` |
| `mask` / `annotate` | 1系統 | 25MB | `{stem}-masked.png` / `-annotated.png` |
| `pdf-images` | ページ範囲 | PDF上限 | `{stem}_p03_img02.png` |

複数枚の正本は既に **20**。「枚数でツールを選ぶ」は 50 や 100 を新発明せず、**この 20 に揃える**。

### 9.2 枚数 — 三役判定

| ROLE | 判定 |
|------|------|
| **CPO** | 同時処理上限は **20枚**。webp-to-jpg と同じ数字で「SUGUDASUの画像はだいたい20まで」を横断の期待にする。数百枚ECは Outside。1枚だけでも完了できる（複数は任意）。 |
| **HCI** | 上限をツールごとに変えると「今回は何枚まで？」の学習コストが毎回かかる。ゲート文言も `最大20枚` で横並び。超過は無効化 + 短い理由1行（Normalizeの行数ゲートと同型）。 |
| **シニアUIUX** | ドロップ面のヒントに最初から「最大20枚」。あとから弾くより入口で揃える。ZIP一括は webp-to-jpg と同様 **約束しない**（逐次DL可）。 |

**確定（草案）:** `MAX_FILES = 20` · `MAX_FILE_BYTES = 25MB`（既存と同一）。合計MBの別ゲートは 11/15 実測。

### 9.3 出力ファイル名 — 三役判定

原則: **元を残す · 何をしたかフォルダで分かる · リネームさせない · コーデック名を出さない**。

| 既存の型 | 例 | 提出リサイズへの含意 |
|----------|-----|----------------------|
| 拡張子だけ | `photo.jpg` | 寸法・容量変更が分からない → **不足** |
| 寸法接尾 | `photo-1200x800.png` | Web長辺・辺を落としたときに強い |
| 動詞接尾 | `photo-masked.png` | プリセットタグに流用 |
| 構造接尾 | `doc_p03_img02.png` | 本件には不要 |

| ROLE | 判定 |
|------|------|
| **CPO** | 提出用が一目で分かること。元と同名は禁止（上書き・取り違え）。プリセットごとに接尾辞を固定。命名テンプレ設定は作らない。 |
| **HCI** | 名前に Quality / MozJPEG を入れない。辺を落としたときだけ `WxH` を足し、結果一覧の「犠牲」とファイル名を一致させる。同一バッチの衝突は `_02` ゼロ埋め（watermark / pdf-images 文化）。 |
| **シニアUIUX** | `sanitizeBaseName`（watermark 既存）を再利用。日本語 stem は残す（実務の手がかり）。日時スタンプ必須や命名ダイアログは禁止。 |

**確定（草案）— テンプレ**

```
{sanitizeStem48(元stem)}_{presetTag}[_{W}x{H}][_{nn}].{ext}
```

| preset | `presetTag` | `_{W}x{H}` | ext |
|--------|-------------|------------|-----|
| `mail_attach` | `mail` | **元と出力のピクセル寸法が違うときだけ** | 原則 `jpg` |
| `form_2mb` | `2mb` | 同上 | 原則 `jpg` |
| `web_long_edge` | `w1200`（長辺値） | **同上**（長辺だけ変われば通常は付く。タグ `w1200` と二重でも可読性優先で寸法は条件付き） | 原則 `jpg` |

- `sanitizeStem48`: watermark の `sanitizeBaseName` を使い、**stem は最大48文字**（メール添付欄・パス長。一次の80からセカンドで短縮）。  
- 衝突 `_nn`: **入力順（ドロップ／選択順）で 02, 03…**。辞書順に並べ替えない。  
- presetTag は用途ラベルのみ。Gmail / LINE / Instagram 等の **媒体名は付けない**。

例: `見積スクショ_mail.jpg` · `見積スクショ_2mb_1600x900.jpg` · `hero_w1200_1200x675.jpg` · 衝突時 `見積スクショ_mail_02.jpg`

**禁止:** `_resized` / `_compressed` / `_mozjpeg` / 日時必須 / 命名ダイアログ / 元名破棄の連番のみ。  
**ZIP名:** 今は約束しない。付けるなら `{stem}_submit_{presetTag}.zip`。

### 9.4 Gemini「よくある仕様 · 命名パターン」役員会突合（2026-08-15）

**材料:** Gemini 概要（縦横比維持 · 長辺/短辺 · 余白 · 拡大防止 · 一括形式変換 · SNS/PPT推奨サイズ · 命名4型）。  
**セカンドオピニオン用:** [`../prompts/image-batch-resize-how-second-opinion-COPYPASTE.md`](../prompts/image-batch-resize-how-second-opinion-COPYPASTE.md)

#### 仕様カタログ → 判定

| Gemini項目 | 判定 | 置き場 / 理由 |
|------------|------|----------------|
| 縦横比の維持 | **採用（既定）** | 提出プリセットの裏動作。トグルに出さない（壊さないのが普通） |
| 長辺指定 | **採用** | `web_long_edge` · メール/2MBの裏でも使う |
| 短辺指定 | **非採用（今期）** | 需要が長辺・容量に偏る。UI増やすな |
| 拡大防止 | **採用（既定）** | `image-trim` の拡大警告と同型。小さい原画を引き延ばさない |
| 余白追加（白/黒パディング）で枠に揃える | **非採用（この HOW）** | SNS/固定枠は既に **`image-trim`**。一括提出 HOW に混ぜると識別が壊れる |
| 一括ファイル形式変換（JPEG/PNG/WebP） | **非採用（主機能）** | `webp-to-jpg` が担当。提出 HOW の主出力は原則 jpg |
| SNS推奨サイズ一覧（IG/X/ストーリー等） | **非採用（この HOW）** | 既に `image-trim` プリセット。二重カタログ禁止 |
| PPT 16:9 / 4:3 推奨サイズ | **PARK（観測）** | 提出・貼付の隣ではあるが、今期プリセット3枠を増やす理由にしない。需要が目立てば `slide_16x9` を第4候補として 11/15 再審 |

#### 命名4型 → 判定

| Gemini型 | 例 | 判定 |
|----------|-----|------|
| 1. サイズ接尾 | `photo_1080x1080` / `photo_w1200` | **条件付き採用** — **出力寸法が元と違うときだけ** `_{W}x{H}`。用途は `w1200` タグ |
| 2. 用途・メディア名 | `banner_instagram` | **一部採用** — SNS媒体名は `image-trim` 側。提出 HOW は `mail` / `2mb` / `w1200`（用途タグ）。`instagram` は付けない |
| 3. 元名を捨てて連番だけ | `image_001` | **Reject** — 元の手がかりを消す。衝突時の `_02` のみ許可 |
| 4. ステータス語 | `product_resized` / `_small` | **Reject** — 何の提出条件か分からない。§9.3 で禁止済み |

#### 各 ROLE（要約）

| ROLE | 意見 |
|------|------|
| **CTO** | 縦横比維持・拡大防止は実装既定でよい。パディングは別キャンバス合成で複雑度が跳ねる。短辺モードは分岐コストに見合わない。命名は `sanitizeBaseName` + 決定論テンプレのみ。 |

## 10. エッジケース（バッチ混在 · 2026-08-15）

**原則:** バッチは **枚ごとに独立** に処理する。寸法や形式が揃っている必要はない。揃っていないことをエラーにしない。  
**対比:** `webp-to-jpg` は入力 WebP のみ（形式を揃えるツール）。本 HOW は提出適合なので **JPEG / PNG / WebP 混在を受理**する。  
**対比:** `watermark` は 20 枚超で「超えた分は追加しない」。本 HOW も同型（全部拒否しない）。

### 10.1 寸法がバラバラ（いちばん普通）

| 状況 | 扱い |
|------|------|
| 20枚の幅・高さがすべて違う | **正常**。プリセットを枚ごとに適用。結果一覧に枚ごとの前後寸法・容量 |
| 一部は既に長辺≤1200、一部は 4000px | 小さい方は **拡大しない**（拡大防止）。大きい方だけ縮小。一覧で「変更なし / 縮小」を分ける |
| 一部は既に 2MB 未満 | `form_2mb` でも **再エンコードはしてよい**（EXIF除去・正立・出力名規則のため）。ただし寸法を落とす必要がなければ落とさない。容量が元より増えたら一覧で注意（稀） |
| 1枚だけ極端に大きい（長辺8192超） | 既存どおりデコード前/作業用に長辺キャップ。処理不能ならその行だけ失敗、他は続行 |
| 横長と縦長が混在 | すべて **長辺** 基準。短辺モードは持たない |

**UIに出さないもの:** 「寸法を揃えてからドロップしてください」。混在は前提。

### 10.2 形式が混在（JPEG / PNG / WebP）

| 状況 | 扱い |
|------|------|
| JPEG+PNG+WebP が同じ DnD | **受理**。デコード →（正立・必要なら縮小）→ **出力は原則 JPEG**（提出プリセット） |
| PNG（透過）と JPEG が混在 | 透過枚は白背景合成して JPEG。不透明 PNG も JPEG。結果行に「背景を白にしました」は透過があった枚だけ |
| 全部 JPEG | 同上パイプライン。形式揃えダイアログは出さない |
| 入力が WebP のみ | 本 HOW で処理してよい（webp-to-jpg へ強制誘導しない）。境界FAQで「形式だけ変えたいなら webp-to-jpg」は可 |
| GIF（静止/アニメ） | **静止1フレームのみ**試すか、非対応で行失敗。アニメ保持はしない。今期は **非対応（行スキップ）** を既定にし、受付拡張は 11/15 |
| HEIC / AVIF / BMP / TIFF | **行スキップ**（対応形式の短い列挙を入口に）。バッチ全体は止めない |
| PDF を画像としてドロップ | **拒否（行）**。pdf-images / 別ツールへ。ここは画像ラスタのみ |
| 拡張子と中身不一致 | デコード成功なら中身優先。失敗なら行スキップ |

**禁止:** 「JPEG に揃えてから再度ドロップ」を必須にするウィザード。混在を一括拒否。

### 10.3 枚数・容量ゲート

| 状況 | 扱い（watermark / webp-to-jpg に合わせる） |
|------|---------------------------------------------|
| 21枚以上ドロップ | 先頭から **20枚まで受理**。超えた分は追加しない + 1行メッセージ |
| 既に20枚ある状態で追加 | 空き枠だけ追加。満杯なら追加しない |
| 1枚が 25MB 超 | その行だけ拒否。他は続行 |
| 合計が数百MB | 逐次処理・1枚ずつ解放。メモリで落ちたら「枚数を減らして」行/全体メッセージ。ZIP強制はしない |

### 10.4 部分成功・失敗

| 状況 | 扱い |
|------|------|
| 20枚中3枚デコード失敗 | 17枚は成果物あり。失敗3行に理由コード相当の短い文言（本文・パスは出さない） |
| `form_2mb` で5枚が未達 | 15枚は DL可。未達5枚は成功バッジを付けない。一括DLは **成功分のみ** or 成功分+未達を分ける（実装時は成功分のみが安全） |
| 全枚失敗 | プライマリ完了にしない。入口を残す |
| 同名ファイルが複数（`a.jpg`×3） | stem 衝突 → `_02` `_03`（入力順）。中身が違っても名前が同じなら連番 |

### 10.5 中身の癖

| 状況 | 扱い |
|------|------|
| Orientation だけ違うスマホ写真混在 | 枚ごとに正立化。ユーザーに回転UIは出さない |
| CMYK JPEG | ブラウザがデコードできなければ行失敗。できれば RGB として出す |
| 破損・0バイト | 行スキップ |
| パスワード付きや暗号化コンテナ | 非対応（出てこない想定） |
| カラープロファイル差 | 観測。今期は触らない |

### 10.6 結果一覧に必須の列（混在を読めること）

| 列 | 意味 |
|----|------|
| 元の名前（短） | 再認 |
| 入力形式 | jpeg / png / webp / その他 |
| 元寸法 → 出寸法 | 変わらなければ「同じ」 |
| 元容量 → 出容量 | |
| 状態 | 成功 / 変更なし（既に条件内） / 未達 / スキップ（形式） / 失敗 |
| 注記 | 白背景 · 拡大せず 等、その行だけ |

一括の「全部同じサイズになりました」を約束しない。約束するのは **同じプリセット規則を各枚に適用した**こと。

### 10.7 ROLE 一眼

| ROLE | 判定 |
|------|------|
| **CTO** | 混在はパイプラインを1本にすればよい。形式ゲートでバッチごと fail すると実装も体験も壊れる。行単位の status enum を先に決める。 |
| **CPO** | 混在拒否は JTBD（フォルダから雑多に投げたい）を殺す。webp-to-jpg との差は「入力を揃えるな」で説明できる。 |
| **HCI** | 混在を警告バナーで騒がない。結果の状態列で足りる。成功と未達を同じ緑にしない。 |
| **認知科学** | 「20枚ドロップ＝20枚成功」の期待を、部分成功のときに壊さないよう件数サマリ（成功17 · 未達2 · スキップ1）を上に置く。 |

## 11. 既存プロダクト連携 · ユースケース（EC · watermark 等）

**問い:** 提出リサイズのあとに透かし（`watermark`）へ、20枚をシームレスに渡すべきか。コピーして持っていくのか。

### 11.1 既存の「連携」の型（事実）

| 型 | 例 | 運ぶもの | 上限感 |
|----|-----|----------|--------|
| **sessionStorage handoff（1回限り）** | 印鑑→請求書 · テストデータ→Normalize | 印1枚の dataURL / CSV テキスト | 小さいペイロード。**画像20枚の dataURL は容量で破綻しやすい**（数MB〜数十MB） |
| **next-path（A17）** | `data-sg-next-*` · `tool-next-path.json` | リンクと理由文だけ | バイナリは運ばない。ユーザーが次ツールで改めて入力 |
| **ユーザーの持ち帰り** | DL / ZIP / クリップボード | OS のファイル | ツール間の契約なし。再ドロップが正攻法 |
| **同一エンジン再利用** | watermark の ZIP → pdf-images が import | コード共有 | ランタイムの素材引き渡しではない |

**ないもの:** 画像バッチをツール間で自動注入する共通バス。Platform SDK 的な「パイプライン製品」は Tech Adoption でも先作り禁止。

### 11.2 想定ユースケースと判定

| ユースケース | 流れ | 判定 |
|--------------|------|------|
| EC商品写真をフォーム/メール用に軽くする | DnD → 提出プリセット → DL | **本 HOW の主座** |
| 軽くしたあと社外送付用に透かし | リサイズ完了 → **次に透かし**（next-path）→ ユーザーが成果物を watermark に再ドロップ | **Adjacent として推奨導線のみ**。バイナリ自動引き継ぎは今期しない |
| リサイズした複数枚を赤入れで次々に隠す | 下記 §11.6 | **自動一括注入は Reject**。枚切替キューは **annotate 本体の別 HOW**（今期必須にしない） |
| 透かししてから容量を落とす | watermark 完了 → 提出リサイズへ next-path | **順はどちらでも可**。両方向の自動パイプラインは作らない（逆方向自動追加禁止と同型の慎重さ） |
| SNS枠に切ってから容量 | `image-trim` → 提出リサイズ | next-path 候補。1枚世界と20枚世界が違うので「切ったPNGをまとめて」はユーザー操作 |
| WebPだけJPEGにしたい | `webp-to-jpg` | 本 HOW に統合しない。混在提出は本 HOW |
| 仮置きに20枚置いてからリサイズ | clip-stash → ? | **Reject**。仮置きに加工を足さない（CASE-011）。仮置きから外へ出して本ツールへ |

### 11.3 「20枚を watermark にどう持っていくか」

| 案 | 判定 | 理由 |
|----|------|------|
| sessionStorage に20枚の dataURL/Blob を載せて自動遷移 | **Reject（今期）** | ストレージ上限・巨大化・失敗が黙る・「連携基盤」化。stamp の1枚手書きとはスケールが違う |
| IndexedDB 共有ストアでツール間キュー | **Reject（今期）** | Platform 先作り。Continue Later / 仮置きと責務が混線 |
| クリップボードに20枚コピー | **Reject** | ブラウザが複数画像クリップボードを実務レベルで保証しない |
| 成果を **1枚ずつ or ZIP で DL** → watermark に DnD | **Adopt（正攻法）** | 持ち帰りが SUGUDASU の出口。watermark は既に複数枚 DnD・ZIP出しがある |
| 成功分だけ ZIP して「透かしへ」で保存ダイアログ | **PARK** | ZIP は webp-to-jpg で約束していない文化。本 HOW も ZIP 必須にしない。需要が強ければ 11/15 で「成功分ZIP（任意）」のみ再審 |
| next-path「次に透かしを入れる」 | **Adopt** | バイナリは運ばない。理由文例:「社外に出す前に透かしを足すとき」 |

**シームレスの定義を誤らない:**  
シームレス＝ユーザーが **同じ規則のファイル名のまま** フォルダから watermark に投げ直せる、まで。  
シームレス≠サーバーもストレージも介さずタブ遷移だけで20枚が消えて現れる、ではない（それは別製品）。

### 11.4 ROLE

| ROLE | 意見 |
|------|------|
| **CPO** | ECの「縮小→透かし」は同一仕事系列の直前直後なので Adjacent は認められる。ただし **1画面パイプライン化はしない**（JTBDが二つ）。next-path で順序を示唆し、素材の移動は持ち帰り。 |
| **CTO** | 20枚バイナリ handoff は stamp パターンの安易な拡大。QuotaExceeded とメモリが本番事故になる。コード共有（resize util）とランタイム引き継ぎを混同しない。 |
| **CMO** | 「SUGUDASUなら縮小も透かしも」は Hub カード群で語る。個別ツールの自動連携を売りにすると Impix/Canva 的スイート比較になる。 |
| **HCI** | 自動で次ツールに飛ぶと、今終わった仕事（容量）と次の仕事（透かし位置）の文脈スイッチが強制される。DLしてから次、の方が区切りが明確。 |
| **認知科学** | ファイル名規則（`_mail` / `_2mb`）が連携の手がかり。自動注入より「フォルダで見つけて再ドロップ」の方が追跡可能。 |
| **シニアUIUX** | 透かしツールに「リサイズ済みを受け取る」専用入口を足さない。同じ DnD 面で足りる。 |

### 11.5 今期の連携契約（文書）

1. 本 HOW の出口は **枚ごと DL（成功分）**。ZIP は約束しない。  
2. `watermark` / `annotate` へのバイナリ自動 handoff は作らない。  
3. 出荷するなら **next-path**（例: 提出リサイズ → watermark）を A17 でジャッジ。annotate 向けは **1枚作業の示唆**に限定。逆方向は自動追加しない。  
4. 実装時に resize 核を thin shared にするのは可（Tech Adoption）。**体験パイプラインの shared は不可**。  
5. 赤入れの複数枚切替は **annotate 側 PARK**（§11.6）。本 HOW の出荷条件にしない。

### 11.6 赤入れ（annotate）への複数枚 · 画像切替

**事実:** 現行の赤入れは **画像1枚**（または **PDF1本のページ切替**）。複数画像ファイルのキュー／サムネ切替はない。PDFの `pdfPageStore` は同一文書のページ単位であり、リサイズ成果物20枚のギャラリーではない。

**ユースケースの中身:** 「縮小済みスクショを何枚も、同じ道具で隠して持ち帰る」——効率の本体は **赤入れ側の枚切替** であり、リサイズ→赤入れの自動パイプではない。

| 案 | 判定 | 理由 |
|----|------|------|
| リサイズから sessionStorage/IDB で20枚を赤入れに注入し切替 | **Reject** | watermark 案と同型。Quota・状態・Undoが枚ごとに爆発。リサイズ HOW の範囲外 |
| 赤入れに「画像キュー（最大N枚）・切替・枚ごと保存」を足す | **PARK（annotate の HOW）** | JTBDとしては理解できる。ただし **赤入れの製品変更**。提出リサイズの出荷条件にしない。Undo/選択/未保存の切替確認が必須で、会議室だけでは決めない |
| リサイズ成果を DL → 赤入れに1枚ずつ開き直す | **Adopt（今の正攻法）** | 1枚世界のまま。命名規則でフォルダから次を拾える |
| next-path「次に赤入れ」 | **条件付き Adopt** | **1枚作業の示唆**向き。『20枚を一括で渡す』とは書かない |
| 仮置きに20枚→赤入れ | **Reject** | 仮置きに加工導線を足さない |
| PDF化して赤入れのページ切替を流用 | **Reject** | 画像バッチをPDFに包むのは別JTBD・品質事故 |

**watermark との差:** 透かしは既に **複数枚一括処理**（同じ設定を全枚に適用）がある。赤入れは **枚ごとに違うマスク位置** が本質なので、一括適用モデルがそもそも合わない。切替キューが要るなら annotate 側。一括注入が要るならなおさらパイプライン化は誤り。

| ROLE | 意見 |
|------|------|
| **CPO** | 効率の痛みは認めるが、解く場所は annotate。提出リサイズに『赤入れモード』を足さない。 |
| **CTO** | 枚切替は shapes・undo・baseCanvas をスロット化する設計変更。resize handoff のついでにやると両製品が壊れる。 |
| **HCI** | 切替時に未保存注釈をどうするかが本丸。自動注入より先に、annotate 単体の「次の画像」UXを Prototyping すべき。 |
| **シニアUIUX** | PDFページ切替UIを画像ギャラリーに流用すると、文書とファイル束が同じ操作に見え危険。 |

**公開 roadmap:** 載せない（2026-08-15 確定）。`considering` は公開の優先シグナル。annotate キューは HOW §11.6 と台帳の PARK で足りる。再開は annotate 単体 HOW 草案のあと。連携パイプライン文言は書かない。提出リサイズ本体の公開 roadmap は **11/15 HOW レビュー後**、Hub/GSC を見てから再審。

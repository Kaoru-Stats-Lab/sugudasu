## 3. Zenn

### 仮タイトル案

|   | タイトル案                                               |
| - | --------------------------------------------------- |
| ★ | **文書差分を「見つける」から「判断できる」へ：SUGUDASU変更確認の設計**           |

### 想定読者

> DOCX / PDFの文書比較機能を設計・実装しており、「差分を検出する」だけではなく、曖昧さや変換損失をどうユーザーに伝えるか悩んでいる開発者。

### 読後にできるようになること

1. 文書比較における「検出」と「判断表示」を分離して考えられる。
2. 不確かなMatchをChangeとして確定しない設計意図を理解できる。
3. PDF/DOCXの構造的なLossを隠さず扱う考え方を理解できる。

### 見出し構成

| H2                                | 意図                                      |
| --------------------------------- | --------------------------------------- |
| **文書Diffで本当に難しいのは「違いを見つけること」なのか** | 単純な文字列Diffとの問題設定の違いを提示。                 |
| **文書をそのままDiffしない**                | Parser → Raw → Normalizer → 比較という境界を説明。 |
| **CandidateとChangeを分離する**         | 不確かな対応関係を変更として誤表示しない設計を説明。              |
| **Loss Awareにする**                 | 読み取れない情報を「差分なし」に見せない考え方。                |
| **表はCell DiffではなくAtomicに扱う**      | 表構造の不確実性とUX上の判断を説明。                     |
| **なぜOCRを入れないのか**                  | スキャンPDFを無理に比較対象へ含めない境界判断。               |
| **RendererはDiff Engineから分離する**    | 検出モデルと表示・Reviewモデルを分離する理由。              |
| **文書比較を「承認判断」の近くまで持っていく**         | 技術設計が最終UXにどうつながるかを整理。                   |

### 必須で触る事実

* [ ] Parser ≠ SLIR
* [ ] Raw Document Model → Normalizer → SLIR
* [ ] Candidate ≠ Change
* [ ] Candidateを自動的にModifiedへ昇格させない

* [ ] Cell DiffをMVPに含めない
* [ ] OCRを採用しない理由

## 尖った少数意見

### 1. noteは「変更確認の紹介記事」にしない方がいい

むしろ、

> **「全部読み直す」という仕事のやり方そのものを疑う記事**

にしてしまう案があります。

プロダクト紹介は最後まで薄くして、読者が「自分も毎回これやってる」と気づいたところで変更確認へ送る。

採用するならかなり尖りますが、noteとの相性は良いです。

### 2. Zennでは「OCRしない」を主役級にしてよい

普通なら「OCR対応しました」が機能追加として語られます。

逆に、

> **「なぜOCRしないのか」**

を技術判断として真正面から扱う。

これは「できないから逃げた」のではなく、**不確かな情報を確かな差分として表示しないための境界設計**として説明できる。

SUGUDASUの「非送信」と同じく、技術的制約を隠さず設計思想として見せられる可能性があります。
